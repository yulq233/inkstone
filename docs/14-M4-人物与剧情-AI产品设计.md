## 2. 市面产品调研综述

### 2.1 调研范围

四路检索：① 国内垂直 AI 写作工具；② 海外专业小说工具（Novelcrafter / Sudowrite）；③ 国内网文平台官方助手；④ Novelcrafter Codex 数据模型的官方文档细节。

### 2.2 对比表（产品 × 关键能力 × 砚台可借鉴点）

| 产品 | 人物刻画 | 大纲设计 | 特色机制 | 砚台可借鉴点 |
| --- | --- | --- | --- | --- |
| **Novelcrafter**（海外，$50/年，BYOK 300+ 模型） | Codex 条目：类型/名称/别名/标签/缩略图/提及追踪；Details 自定义字段；Research 区（只给人看、不进 prompt） | Outline / Grid / Matrix 多视图 | ① 正文提及自动追踪（别名不区分大小写匹配，可关）；② Relations 关系聚合（提"五人议会"自动带上全员卡片）；③ AI Settings 的 **Always Include**；④ 条目是"活文档"，编辑器内所见即最新版 | **Codex 数据模型原型**（§4.1 直接对标）；别名机制；"AI 知道的"与"人用的"分区 |

| **番茄·作家助手** | 人物小传 | 大纲 + 热点贴合/流量预测 | 平台流量数据 | 不借鉴（依赖平台数据，与本地优先冲突） |
| **七猫** | 人物卡片 | 故事地图 | — | 故事地图的"章节 × 人物"矩阵视图（Grid 视图同族） |

| **蛙蛙写作** | 起名器 | — | 素材库、**随机金手指** | **灵感随机器**（低成本、纯本地可做一部分） |

### 2.3 行业结论（八条设计启示）

1. **续写/扩写/改写/大纲生成已是标配**，砚台 P0/P1 已覆盖——这次的功能是拉开差距的部分，不是补标配。
2. **人物管理的成熟范式 = wiki 式数据库 + 别名 + 自动提及追踪**（Novelcrafter 验证得最充分）。没有追踪的人物卡会随篇幅增长迅速失真、无人维护。
3. **"防崩人设"的正确分层**：确定性规则先跑（年龄/瞳色/生死状态按章冲突），语义疑点再交模型复核——砚台 `docs/01` §一致性校验两段式决策与此完全吻合，起点的人设字段化给出了字段清单参考。
4. **大纲的成熟范式 = 三层（总纲→卷纲→章纲）+ 章纲与正文双向关联**（阅文大纲树）。单层大纲在长篇里必然失控。
5. **伏笔是独立实体不是大纲里的一句话**（阅文单列伏笔模块）：登记埋设章、预期回收点、状态，超期未回收给提醒。
6. **"AI 知道的"与"人用的"必须分区**（Codex 的 Description vs Research 区）：作者随手记的草稿、灵感图链接不该进 prompt。
7. **AI 产物一律进候选，采纳才落盘**：所有 AI 生成结果都不直接改设定/大纲文件——这既是产品共识，也与砚台"AI 不越权写文件"的既有边界一致。
8. **数据主权已是真实卖点**：行业白皮书显示国内多家工具以"默认不上云"作差异点——砚台的本地优先 + BYOK 不是妥协，是立足点，设计里不能为了功能丰富度偷偷破坏它。

## 3. 砚台的差异化定位（一句话）

> **同样的"人物库 + 大纲 + AI 生成"能力，别人锁在云端订阅里，砚台把它做成本地文件 + 你自己的模型。**

三条支撑：

1. **真源是文件**：人物卡、大纲都是作品目录下的 Markdown，用户可以脱离砚台用任何编辑器维护、可以用 git 版本化、换工具不锁死。这是 Novelcrafter（云端库）和国内平台（平台资产）都给不了的。
2. **BYOK + 纯本地可选**：人物小传/大纲生成走用户自己配的模型（本地 Ollama = 零外发），外发前有预览与确认闸门（P1-b 3b 刚落地，正好复用）。
3. **记忆金字塔装配**：别人把"人物卡全文塞 prompt"，砚台按 L0~L5 预算装配——本章提及的人物进 L0 精选，其余降级为 L1 摘要。长篇不爆 token，这是砚台既有架构的直接红利。

## 4. 功能设计

### 4.0 功能地图（R1/R2 硬性在前，R3 补充在后）

```
M4 人物与剧情
├── A. 人物原型刻画（R1 硬性）
│   ├── A1 人物卡：文件层 + 编辑 UI
│   ├── A2 别名归一
│   ├── A3 AI 生成小传候选（刻画助手）
│   ├── A4 人物关系网
│   └── A5 防崩人设校验
├── B. 剧情大纲设计（R2 硬性）
│   ├── B1 三层大纲：总纲 / 卷纲 / 章纲（文件层 + 编辑 UI）
│   ├── B2 章纲 ↔ 正文双向关联
│   ├── B3 AI 生成大纲候选（总纲/卷纲/章纲各有装配策略）
│   ├── B4 编辑视角大纲体检
│   └── B5 伏笔登记与回收提醒
└── C. 补充功能（R3 授权，自选）
    ├── C1 世界观/设定条目（地点/势力/物品/规则，与人物卡同一套 Codex 机制）
    ├── C2 一致性校验扩展（两段式，复用 A5 引擎）
    ├── C3 灵感随机器（金手指/随机事件/起名，纯本地为主）
    └── C4 入口整合（斜杠指令 + 快捷面板 + 侧栏新面板）
```

### 4.1 A1 人物卡（数据模型）

**对标**：Novelcrafter Codex anatomy（官方文档逐字段核对）+ 起点数据化人设。按砚台"真源 Markdown"约定落盘。

**文件形态**：一人一文件，`<作品根>/codex/characters/<slug>.md`，YAML frontmatter 存结构化字段，正文存自由描述。

```markdown
---
type: character          # character | location | faction | item | concept（C1 复用）
name: 沈观澜
aliases: [观澜, 沈先生, 老沈]   # A2 别名归一的数据源
tags: [主角, 云京司]            # 仅供人组织筛选，不进 prompt（对标 Codex tags）
fields:                  # 起点式数据化字段，键可自定义；AI 候选只写已知键
  年龄: 二十七
  身份: 云京司主事
  性格标签: [谨慎, 重诺, 记仇]
  成长弧线: 从明哲保身到主动担责
  状态: 在世            # 供 A5 确定性校验（死亡后出场即规则命中）
summary: >-              # 50~100 字核心梗概，进 L0 精选的原料
  云京司最年轻的主事，因旧案背负污名，谨慎外表下藏着翻案的执念。
ai:                      # AI 注入策略（对标 Codex AI Settings）
  alwaysInclude: false   # true = 任何生成请求都带上此条（用于世界观基石条目）
relations:               # A4 关系网；双向写入，指向对方 slug
  - { to: 沈砚之, kind: 父子, note: 断绝往来多年 }
timeline:                # 按章取值变更点（docs/01 既有决策）
  - { chapter: 3, field: 状态, value: 重伤 }
---

（正文 = 自由描述 + 作者草稿，Markdown 原样存储）
```

**设计理由**：

- **frontmatter 承担结构化、正文承担自由度**：`fields` 是开放键值而不是固定 schema——起点的人设字段每本书关注点不同（仙侠要灵根，刑侦要验伤能力），固定 schema 会逼用户填无用字段。确定性校验（A5）只认声名显赫的少数键（`状态`/`年龄` 类），其余键给人看。
- **summary 与正文分开**：对标 Codex"Description 进 prompt、Research 不进"的分区经验——L0 装配用 summary，正文草稿永不外发。
- **timeline 记变更点**而非全量快照：`docs/01` 已定"人物属性按章取值"，只存 diff 体积最小且可回放。

### 4.2 A2 别名归一

- 数据源：`aliases` 数组。既有决策（记忆金字塔节）已明确：**`name + aliases` 必须注入 jieba 词典**，否则中文人名被切碎、提及命中骤降。
- 编辑器内提及识别属 M2（索引 + TipTap 装饰层），本期内做**离线版**：扫正文 → 输出"每章提及了哪些人物"清单，供 B3 装配策略与 A5 校验用；编辑器内高亮下划线 + 悬浮卡片是 M2 交付，此处只预留接口。

### 4.3 A3 AI 生成小传候选（人物原型刻画的核心动作）

**产品形态**：人物卡编辑页的「AI 刻画」区，四个动作：

| 动作 | 输入装配（记忆金字塔） | 输出候选 |
| --- | --- | --- |
| 生成小传 | 该人物 summary 现值 + 近 N 章中该人物的原文片段（L3 检索）+ tags/fields | summary 候选（50~100 字） |
| 扩写描述 | 现有正文 + L1 摘要 + 检索命中片段 | 正文追加候选（diff 预览） |
| 补全字段 | 按字段名定向检索（如"性格标签" → 近章该人物言行片段） | 逐字段候选，勾选采纳 |
| 关系推断 | 两张人物卡 + 共同出场章节片段 | relations 候选（人工确认后双向写入） |

**三条产品边界**（行业共识第 7 条 + 砚台既有边界）：

1. 候选进**候选条 UI**（复用 P1 已落地的候选条组件与交互），用户逐条采纳，**采纳才写文件**——AI 永不直接改设定文件。
2. 全部走 sidecar 既有通道，**外发前过预览 + 确认闸门**（`/ai/preview` + EgressConfirmDialog，P1-b 3b 现成）。
3. 纯本地模式下本地模型同样可用；被闸门拦下时文案按 3b 的三态徽标约定（"不会真的发送"）。

### 4.4 A4 人物关系网

- 存储：人物卡 `relations` 数组（如上），指向 slug + 关系类型 + 一句话备注。不引入图数据库，**可视化后置（§8 决议 #1）**：P1 只交付关系列表，数据结构按图设计好，M2 之后视需要再加力导向图，届时零数据迁移。
- AI 用法见 A3「关系推断」。Relations 聚合注入（Codex 的"提到五人议会自动带全员卡"）依赖装配策略，列入 B3 的装配规则表。

### 4.5 A5 防崩人设校验（两段式）

**第一段（确定性规则，本地秒出，不耗 token）**：

| 规则 | 数据来源 | 例 |
| --- | --- | --- |
| 属性按章冲突 | `timeline` diff + 全文扫描 | 第 5 章"左眼有疤"，第 12 章外貌描写无疤 |
| 生死状态 | `fields.状态` + 提及清单 | 标记`已故`后仍在对话章出现 |
| 年龄推算 | `fields.年龄` + 时间线标记 | 三年后的章节年龄没涨 |
| 称谓漂移 | aliases + 正文扫描 | 全文只有"老沈"，`沈先生`从未出现（提示别名冗余） |

**第二段（语义复核，模型批处理）**：第一段筛出的疑点 + 相关原文片段交模型判断"是真崩了还是合理剧情（易容/回忆/尸变）"——**模型只做裁判，不做扫描**，成本可控。

### 4.6 B1 三层大纲（文件层）

```
<作品根>/outline/
├── 总纲.md          # 一本书一份：核心冲突、主线、结局方向
├── vol-01.md …      # 卷纲：本卷目标、关键节点、卷末钩子
└── ch-0003.md …     # 章纲：与章节 id 关联（frontmatter chapterId）
```

- 章纲 frontmatter 记 `chapterId`，**章节删除时章纲不删、标记 orphan**（对齐 `docs/01`"定位失效进待办，不静默丢弃"的既有原则）。
- 章纲正文字段建议但**不强制**：本章目标 / 出场人物（slug 列表，供装配）/ 钩子 / 伏笔动作（见 B5）。

### 4.7 B2 章纲 ↔ 正文双向关联

- **章纲 → 正文**：写作界面侧栏显示当前章的章纲（可折叠），一键插入为编辑器顶部引用块（不污染真源，插入的是副本）。
- **正文 → 章纲**：章节保存后对比字数/摘要变化，章纲条目上提示"正文已偏离章纲（本章实际写了 X，纲里是 Y）"——第一版只提示不自动改写。

### 4.8 B3 AI 生成大纲候选

| 生成对象 | 装配策略 | 说明 |
| --- | --- | --- |
| 总纲 | 一句话设想 + 世界观基石条目（`alwaysInclude`）+ 主要人物 summary | 从零到一 |
| 卷纲 | 总纲 + 前卷章纲摘要 + 本卷相关人物卡 | 承上启下 |
| 章纲 | 所在卷纲 + 前一章实际内容摘要（L1）+ 本章出场人物的卡（**按 B2 章纲声明的出场人物优先**，未声明的按提及清单降级为 summary） | 记忆金字塔按预算装配，人物卡全文永不整体硬塞 |
| Relations 聚合注入 | 出场人物的 relations 指到的卡，取 summary 一行 | 对标 Codex 聚合，控制体积 |

产物一律是**候选大纲**，进对比视图（现值 vs 候选），用户接受后写文件；接受动作同样要过外发闸门（生成请求本身发过一次确认，接受只是本地写盘，不再确认——与续写接受同一模型）。

### 4.9 B4 编辑视角大纲体检

对标笔灵"编辑审稿视角"：对总纲/卷纲发起一次"编辑体检"，输出结构化意见卡（节奏 / 主线偏移 / 爽点密度 / 逻辑洞），每条意见可一键转为**待办**——对齐砚台既有"批注锚点失效进待办"的待办机制。

### 4.10 B5 伏笔登记与回收提醒

```yaml
# 章纲 frontmatter 内或独立 foreshadow 条目
foreshadow:
  - id: fs-001
    title: 观澜袖中的半枚铜符
    plantedIn: ch-0003
    expectResolveBy: vol-02   # 可空 = 无限期
    status: open              # open | resolved | dropped
    resolvedIn: null
```

- 确定性扫描：进入新卷时列出 `open` 且超过 `expectResolveBy` 的伏笔 → 侧栏提醒卡（对标阅文伏笔模块；**只提醒，不自动判定"回收了"**——回收判定交模型建议 + 人工确认，属于 A5 第二段同款克制）。

### 4.11 C 组补充功能（一句话级，实施时再详化）

- **C1 设定条目**：地点/势力/物品/规则与人物卡**同一套文件机制**（`type` 字段区分）， zero 额外引擎——这是把 Codex 做成通用 wiki 而不是"人物系统"的原因。
- **C2 一致性校验扩展**：A5 引擎加地点/物品类规则（如"云京到北境三天前还说要一个月"），仍两段式。
- **C3 灵感随机器**：金手指/随机事件/起名三件套；起名器纯本地（语料 + 规则，零外发），金手指/事件可走 AI 但默认先给本地灵感库抽签——对标蛙蛙，成本低、幸福感高。
- **C4 入口整合**：`/` 斜杠指令新增 `/人物` `/章纲` `/伏笔` 等；快捷生成面板新增对应 kind；侧栏新增「设定」与「大纲」两个面板（与外发记录面板同级）。

## 5. 架构对齐清单（逐条核对既有约定）

| 约定 | 本设计的落点 |
| --- | --- |
| 真源是磁盘文件，`.inkstone/` 只存索引 | 人物卡/大纲/伏笔全是作品目录下 Markdown；提及清单等派生数据进 `.inkstone/`（可删重建） |
| AI 调用走 sidecar 单一通道 + 预览确认闸门 | A3/B3/B4/C3(AI 路径) 全部复用 `/ai/preview` + EgressConfirmDialog + 纯本地模式拦截 |
| 记忆金字塔 L0~L5 按预算装配 | B3 装配策略表；人物卡 summary 进 L0，正文永不直接进 prompt |
| 别名注入 jieba 词典 | A2；Codex `name + aliases` 注入是既有决策的强制消费方 |
| 一致性两段式（规则先行、模型复核） | A5/C2 引擎设计 |
| AI 产物不越权写文件 | 候选制 + 采纳落盘；候选条组件复用 |
| 不引入新依赖 | YAML 解析用既有能力（sidecar 已有 py 生态，前端如需解析另行评估 vite 侧纯 JS yaml——实施计划里定）；图可视化首版可降级为列表 |
| 文案红线 | 本地模式下不得出现"已发送/上传"类表述，沿用 3b 三态徽标文案规范 |

**与 M2 的依赖关系（重要）**：编辑器内提及高亮、点击悬浮卡、正文自动追踪**依赖 M2（Codex 索引层）**。本设计的 P0 分期（见 §6）刻意把文件层与 AI 候选链路做在 M2 之前，先行独立可用；追踪与高亮在 M2 落地后接管，接口在 A2 已预留。

## 7. 明确不做（本期）

1. **不做自研微调/小说模型**（Sudowrite 路线）——砚台是编排与装配层，模型是用户的选择。
2. **不做平台流量数据类功能**（热点贴合/流量预测）——与本地优先根本冲突。
3. **不做多人协作/云同步设定库**——v2 `.inksnap` 之外不扩存储形态。
4. **不做"AI 直接改设定/大纲文件"**——永远候选制。
5. **第一版不做强制 schema 的人物模板**——`fields` 开放键值，模板后续作为"预设字段包"另行评估。
