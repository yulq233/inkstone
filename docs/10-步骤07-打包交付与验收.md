## 0. 内部顺序：先打包，后验收

`03` 文档 §10 的"已知坑"里写了这句话：

> **批次 D 第一件事就是跑通打包后启动，不要等到最后**

理由：PyInstaller 打包 FastAPI/uvicorn 缺 hidden-imports 是**开发态完全看不出来**的一类问题 —— 开发时 `.venv` 里什么都有，装完之后 sidecar 起不来，而这时所有验收项都依赖 sidecar。

所以本步骤的顺序是：

```
1. sidecar 能独立打包并启动      ← 先干这个
2. 桌面应用能带 sidecar 打出来
3. 装一遍，走通 A2~A5（拿着安装包，不是 dev 模式）
4. 补齐手工验收清单，逐项签字
5. 记性能基线
```

## 3. sidecar 打包（PyInstaller）

### 3.1 命令与输出

```
pyinstaller
  --noconfirm --clean
  --name inkstone-sidecar
  --onedir                       # 不用 --onefile：启动快、便于增量更新（03 §10）
  --console                      # 保留 stdout：握手就绪行必须能被打包后的进程打印出来
  --distpath  <repo>/apps/desktop/resources/sidecar-dist
  --workpath  <repo>/.build/pyinstaller
  --paths     services/sidecar/src
  --hidden-import uvicorn.logging
  --hidden-import uvicorn.loops.auto
  --hidden-import uvicorn.loops.asyncio
  --hidden-import uvicorn.protocols.http.auto
  --hidden-import uvicorn.protocols.http.h11_impl
  --hidden-import uvicorn.protocols.websockets.auto
  --hidden-import uvicorn.lifespan.on
  --hidden-import anyio._backends._asyncio
  services/sidecar/src/inkstone/__main__.py
```

**`--console` 不能省**：sidecar 的握手靠 stdout 打印 `INKSTONE_READY {...}`。打成 `--windowed` 后没有 stdout，主进程会等 15 秒然后报"启动超时" —— 而 sidecar 其实起来了。这是打包步骤里最隐蔽的坑。

**`--add-data` 必须列数据文件**（M3 起新增）：PyInstaller 只打包它静态分析到的 `.py`，
**非 Python 文件一个都不会带上**。sidecar 里的数据文件：

| 文件 | 缺了它的症状 |
|---|---|
| `inkstone/ai/prompts/*.toml`（提示模板） | `/ai/continue` 与 `/ai/quick` 直接 500 —— 生成类端点起不来，而 healthz 正常，**看起来像"打包成功了" |

加上：`--add-data "services/sidecar/src/inkstone/ai/prompts;inkstone/ai/prompts"`
（Windows 分隔符是 `;`，POSIX 是 `:`）。装好后进 `resources/sidecar/_internal/inkstone/ai/prompts/`
确认文件在，再跑一遍 `sidecar-smoke.mjs`（要给它加一条生成端点的探活）。

### 3.2 hidden-imports 为什么是这些

uvicorn 与 anyio 大量使用**运行时字符串导入**（按配置动态加载 loop / protocol / lifespan 实现），PyInstaller 的静态分析看不到。`03` 文档 §10 已列出清单，此处补全到具体模块名：

| 缺失的模块 | 症状 |
|---|---|
| `uvicorn.logging` | 启动即 `ModuleNotFoundError` |
| `uvicorn.loops.*` / `uvicorn.protocols.*` | 起来但一收请求就崩 |
| `anyio._backends._asyncio` | `async` 端点直接 500 |

**这不是"加上就一劳永逸"**：升级 uvicorn 主版本后要重新核对 —— 加一条自检：打包完成后用真进程跑一次 `scripts/sidecar-smoke.mjs`（它覆盖握手 / 鉴权 / 优雅退出 / 日志脱敏），**对着打包产物跑，不是对着 venv 跑**。

### 3.3 产物布局

```
apps/desktop/resources/sidecar/
└─ inkstone-sidecar/
   ├─ inkstone-sidecar.exe
   └─ _internal/…            # Python 运行时 + 依赖（--onedir）
```

`resources/sidecar/` 整个目录通过 electron-builder 的 `extraResources` 带进安装包（**不能放进 asar** —— asar 内的可执行文件无法被 spawn）。

`.gitignore` 要加：`apps/desktop/resources/sidecar/`（构建产物，几十 MB，不进仓库）。

### 3.4 独立验证（打包后第一件事）

```bash
# 直接跑产物，看它能不能自己握手
cd apps/desktop/resources/sidecar/inkstone-sidecar
INKSTONE_TOKEN=test token 来自 env ./inkstone-sidecar.exe
# 期望：stdout 打印一行 INKSTONE_READY {"v":1,"port":...,"pid":...,"version":"0.1.0"}
# 再用 curl 打 healthz（免鉴权）确认返回 200
```

这一步不通过，后面的桌面打包不用做。

## 4. 桌面打包（electron-builder）

### 4.1 `productName` 用 ASCII —— 一个影响面很大的小决定

| 字段 | 值 | 决定路径？ |
|---|---|---|
| `productName` | **`Inkstone`** | ✔ 决定安装目录、userData 目录 |
| 快捷方式名 / 窗口标题 | `砚台` | ✘ 仅显示 |
| `appId` | `com.inkstone.app` | ✔ |

**为什么不用中文 `productName`**：它会让安装目录变成 `C:\Program Files\砚台\`，`userData` 变成 `%APPDATA%\砚台\`。于是整条链路都要处理非 ASCII 路径：

- PyInstaller 打包的 bootloader 读自身路径
- sidecar 在 userData 下写日志与备份
- Python 的 `pathlib` 与 Windows API 之间的编码往返

这些**大多能工作**，但它们属于"平时没事、出问题时极难定位"的一类。用 ASCII 的目录名一次躲开整类风险，而用户能看到的三个地方（快捷方式、窗口标题、安装器界面）全是中文 —— 没有任何体验损失。

**顺带修一个开发态与生产态不一致**：显式设置应用名，让两端用同一个 `userData`：

```ts
// main/index.ts
app.setName('Inkstone');
app.setPath('userData', path.join(app.getPath('appData'), 'Inkstone'));
```

不设的话，开发态 `userData` 是 `%APPDATA%\Electron`，装完之后是 `%APPDATA%\Inkstone` —— 排查问题时"日志到底在哪"会绕一圈。

### 4.2 `electron-builder.yml`

> ⚠️ **实现已偏离本节**：实际用的是 `apps/desktop/electron-builder.cjs`（JS 配置）。
> 原因见 §11.5 的 M24 行 —— `electronDist` 必须按环境算，而 YAML **不支持** `${env.X}` 展开，
> 只能硬编码绝对路径。本节保留设计时的样子，只作意图参考；真源是 §11.1 与 §11.5。

```yaml
appId: com.inkstone.app
productName: Inkstone
directories:
  output: ../../.build/release
  buildResources: resources

files:
  - out/**/*
  - package.json

extraResources:
  - from: resources/sidecar
    to: sidecar          # → <安装目录>/resources/sidecar/

win:
  target: [nsis]
  icon: resources/icon.ico

nsis:
  oneClick: true                    # 一键装到用户目录，不需要管理员权限
  perMachine: false
  deleteAppDataOnUninstall: false   # 卸载不删稿子。这条是底线
  shortcutName: 砚台
  artifactName: inkstone-${version}-setup.${ext}   # 文件名保持 ASCII
```

三条要点：

1. **`deleteAppDataOnUninstall: false`** —— 卸载时删掉用户的作品是灾难。保持默认，并在注释里写明这是刻意的。
2. **`artifactName` 用 ASCII** —— 安装包文件名走 HTTP 下载、被各种工具处理，中文名容易出问题。
3. **`oneClick: true`** —— 免管理员权限安装到 `%LOCALAPPDATA%`，对个人创作工具是更合适的选择。

### 4.3 脚本

```jsonc
// apps/desktop/package.json
"build":        "electron-vite build",
"build:sidecar":"node ../../scripts/build-sidecar.mjs",
"dist:win":     "pnpm build:sidecar && pnpm build && electron-builder --win --config electron-builder.yml"
```

根 `package.json` 加一条聚合命令，让"出一个安装包"是一条命令的事。

## 5. 生产态路径解析

`main/sidecar/env.ts` 已有开发态逻辑（`.venv/Scripts/python.exe -m inkstone`）。补生产态分支：

```
app.isPackaged === false  →  dev：<repo>/services/sidecar/.venv/Scripts/python.exe  -m inkstone
app.isPackaged === true   →  prod：path.join(process.resourcesPath, 'sidecar', 'inkstone-sidecar', 'inkstone-sidecar.exe')
```

| 约束 | 说明 |
|---|---|
| `INKSTONE_PYTHON` 环境变量**优先级最高** | 已有能力，保留。它的用途是"不想用打包产物、想指到某个 venv"的调试场景 |
| 生产态下**不要**回退到 venv | 装了应用的机器上没有 venv。找不到可执行文件就直接报错并给出路径 —— 静默回退会让"打包漏了 sidecar"表现成"启动超时" |
| `INKSTONE_HOME` 仍传 `userData` | 日志与备份落在 `%APPDATA%\Inkstone`，与开发态同一位置 |

### 6.2 补做项：渲染进程 CSP（步骤 06 的遗留）

步骤 06 的代码审查把它列为遗留项，**它只能在打包产物上做** —— 原因见下面第一条。

#### 为什么不能用主进程注入

原本的想法是在 `app.isPackaged` 时用 `session.defaultSession.webRequest.onHeadersReceived` 往响应里塞 `Content-Security-Policy`。**这条对生产态无效**：生产页面走 `file://` 加载，没有 HTTP 响应头可改，`webRequest` 那组钩子对 file 协议不触发。

`file://` 下唯一能声明 CSP 的地方是 `<meta http-equiv="Content-Security-Policy">`。

#### dev 与 prod 共用同一份 `index.html`，必须按模式注入

Vite 的 HMR 需要内联脚本与 ws 连接，把生产那份严格策略也用在 dev 上会**先把开发环境弄坏**（症状是"改了代码页面不刷新"，很容易被误判成 Vite 的问题）。

做法：在 `electron.vite.config.ts` 的 renderer 里加一个小 plugin，用 `transformIndexHtml`，只在构建时插入：

```ts
function cspPlugin(): Plugin {
  return {
    name: 'inkstone:csp',
    transformIndexHtml: {
      order: 'post',
      handler: (html, ctx) =>
        ctx.server ? html : html.replace('<head>', `<head>\n    ${CSP_META}`), // dev 不注入
    },
  };
}
```

#### 策略起始稿（**必须实测调整，别照抄**）

```
default-src 'none';
script-src 'self';
style-src 'self';
img-src 'self' data:;
font-src 'self';
connect-src http://127.0.0.1:*;
```

| 指令 | 为什么是这个值 |
|---|---|
| `default-src 'none'` | 白名单式收口：没显式放行的都不许 |
| `script-src 'self'` | 打包后入口是 `<script type="module" src="./assets/…">`，没有内联脚本 |
| `style-src 'self'` | 样式在独立 `.css` 文件里。**主题与字号是通过 JS 的 CSSOM 写到 `<html>` 上的，不受 `style-src` 约束**（CSP 拦的是 HTML 里的 `<style>` 与 `style=""` 属性，不是 `el.style.setProperty`）—— 所以这里**先不给** `'unsafe-inline'`，实测有样式被挡再加 |
| `connect-src http://127.0.0.1:*` | 渲染进程**直连 sidecar**，而端口是每次启动自选的（`bind 127.0.0.1:0`）。写死端口会在第二次启动就断连 |
| `img-src data:` | 留给将来可能的内联图标 |

#### 两个必须先探明、再落策略的未知

1. **`file://` 下 `'self'` 的行为**。file 页面的 origin 是 `file://`，"同源"在这个协议下没有明确定义。配错的后果是**自家脚本被挡掉 → 白屏**，比不加 CSP 更糟。
2. **`--allow-file-access-from-files` 之类的开关是否被我们自己设过**（没有就不涉及；有的话要一起核）。

**验法（先探针、后落策略）**：先在 dev 下把同一份策略用 `<meta>` 临时插进 `index.html`，确认页面不白、`window.inkstone` 在、能连上 sidecar —— dev 本来就没有 CSP，正好拿它当"策略是否过严"的探针。确认之后再改成按模式注入，并在打包产物上复测一次。

## 7. 性能基线（WS6.4）

`02` §6.4 的原话："打开 10 万字作品、切换章节耗时 —— 记下数字作为 M1 对比基线"。

### 7.1 测什么

| 指标 | 测法 | 记录单位 |
|---|---|---|
| 冷启动到窗口可见 | 记 `app.ready` → `ready-to-show` 的时间差（临时打日志） | ms |
| 冷启动到 sidecar 就绪 | 主进程日志里"握手成功"的时间戳 − 进程启动时间 | ms |
| 打开 10 万字章节 | `readChapter` 的耗时（DevTools Network 面板） | ms |
| 首次渲染 10 万字 | `setMarkdown` 到编辑器可交互（在 EditorPane 里临时打点） | ms |
| 切换章节（同作品内） | 点击 → 新内容出现（含 flush + read + render） | ms |
| 保存一次（10 万字） | PUT 往返 | ms |
| 侧栏渲染 100 章 | 进入作品到侧栏可交互 | ms |

### 7.2 造测试数据

10 万字的稿子要真的造出来：

```bash
# 生成长度可控的中文正文，含标题/加粗/斜体/引用/分隔线（覆盖白名单全部语法）
node scripts/make-fixture.mjs --chars 100000 --chapters 100
```

这个脚本要**一并交付**（M1 对比基线时还要用同一份数据，否则数字没有可比性）。生成的作品放在临时目录，不进仓库。

### 7.3 记录方式

数字写进验收清单的末尾一张表，格式：`指标 / 数值 / 机器 / 日期 / 备注`。**同一台机器、同一次安装**测完所有项 —— 跨机器比数字没有意义。

## 8. 异常与边界

| 场景 | 处理 |
|---|---|
| PyInstaller 打包后 sidecar 起不来 | §3.4 的独立验证先行；对照 §3.2 的表逐个补 hidden-import |
| 打包产物在中文用户名下运行 | 本机用户名是 ASCII，但**用户机器可能是中文**。手工验收要专门找一台中文用户名的机器测（或用 `C:\Users\测试\` 建一个本地账户）—— 这是 PyInstaller 的历史敏感点 |
| `resources/sidecar/` 漏进安装包 | 主进程报错要**明确说"找不到 sidecar 可执行文件：<路径>"**，而不是"启动超时" |

### 11.2 打包三大坑（WorkBuddy 沙箱与打包的根本冲突）

`pnpm dist:win` 能跑通，是因为绕开了本机沙箱的三个限制。**换环境重跑前先读 `scripts/dist-win.mjs` 文件头注释**：

1. **目录 rename 被整体禁止**：连 2 个文件的小目录 rename 都 EPERM。electron-builder 默认「解压到 `.tmp` → rename 成品」必死。→ `electronDist` 指向本地预解压目录（路径由 `scripts/build-paths.cjs` 统一算出，`electron-builder.cjs` 与 `dist-win.mjs` 共读），electron-builder 只复制不 rename。
2. **工作区内 `*.asar` 被延迟锁定**：electron 自带的 `default_app.asar` 落地几十秒后被常驻服务持续锁定（EBUSY unlink 15 次重试全失败）。→ electron-dist 和 release 输出目录都移到工作区外 `%USERPROFILE%\.inkstone-build\`。
3. **批量删除保护（>50 文件/回合）拦下各步骤的目录清理**：PyInstaller `--clean`、vite `prepareOutDir`、electron-builder 清残留都会删 >50 文件。→ `dist-win.mjs` 给所有子进程注入 `CODEBUDDY_SAFE_DELETE_ENABLED=0`。
