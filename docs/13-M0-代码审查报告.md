## 0. 总体评价

代码质量**明显高于同类 Electron/Python 桌面项目的平均水平**：

- **注释写"为什么"而非"是什么"**，多数决策有实测记录或反例支撑（双 pid 杀进程、`sandbox:false` 的复验方法、`pendingSince` 用 `null` 作哨兵、SSE `frameStart` 设计）
- **纯逻辑与 IO 分离**，可测性强：`settings-io`/`credentials-io`/`autosave`/`chapter-switch`/`gen-state`/`md-adapter` 都不依赖 DOM 或 electron，无 jsdom 环境也能覆盖
- **静态检查全绿**：`mypy --strict` 38 文件 0 错、`ruff check` 全绿、`eslint .` 0 error（5 个显式降级的 warn）、全仓 **无 `any`、无非空断言 `!`、无 `@ts-ignore`**

## 1. HIGH（4 条，全部已复核）

### H1 ✓ `repo.py:489` + `:499` + `:556` — 非 UTF-8 章节：读用 `errors="replace"`、回存按 UTF-8，**原稿字节不可逆损坏**

```python
# :489 读：解码失败不报错，塞 U+FFFD
markdown = raw.decode("utf-8", errors="replace")
# :499 哈希算的是原始字节
"hash": content_hash(raw),
# :556 写：客户端原样回存时按 UTF-8 编码
payload = markdown.encode("utf-8")
```

`read_chapter` 返回的 `hash` 是磁盘**原始字节**的 sha256，渲染进程把它当 `baseHash` 回传，冲突检测**必然通过**——"外部改动保护"在这条路径上完全失效。GBK 文件被解码成含 `U+FFFD` 的字符串，用户改一个字后回存，原 GBK 字节被永久替换为 UTF-8 编码的 `U+FFFD`（不可逆）。

**触发场景**：Windows 上用 GBK 编辑器写过的 `chapter.md`（项目明确支持"用记事本/VSCode 改文件"）。
**修复**：`read_chapter` 改严格解码，`except UnicodeDecodeError` → 抛 `DomainError`（文案指向"文件不是 UTF-8，请先转码"）；或响应带 `encodingSafe:false` 并在 `write_chapter` 拒绝覆盖。**不要**把 `errors="replace"` 的产物写回磁盘。

### H2 ✓ `index.ts:237-245` + `menu.ts:124` + `quit-guard.ts:37,55` — 菜单「退出」/ Cmd+Q 绕过 flush，**静默丢最多 3 秒正文**

```ts
app.on('before-quit', (event) => {
  if (quitting || !supervisor) return;
  event.preventDefault();
  quitting = true;
  // 注释假设：渲染进程的落盘已经在 win.on('close') 里等完了
  void supervisor.shutdown().finally(() => app.exit(0));
});
```

**注释的前提是错的**。Electron 语义：`app.quit()` → 先触发 `before-quit`，**若其中 `preventDefault()` 则整个 quit 被取消，窗口的 `close` 事件根本不会触发**。于是：

| 路径 | 是否 flush |
|---|---|
| 点窗口 X | ✅ `close` → flush → destroy → `window-all-closed` → 再走 `before-quit` |
| 菜单「文件→退出」(`role:'quit'`) | ❌ **直接丢** |
| macOS Cmd+Q | ❌ **直接丢** |

`Autosave` 有 3000ms `maxWait`，所以「正常关闭零丢失」（验收项 A4）在这条路径上不成立，且用户看不到任何提示。

**修复**：`before-quit` 里先让窗口走正常关闭（`for (const w of getAllWindows()) w.close()`），把 sidecar 清理移到 `will-quit`；或让 quit-guard 暴露"请 flush 一次"入口，`before-quit` 先 `await` 它。关键：**flush 完成必须在 `app.exit()`/`shutdown()` 之前**。

### H3 ✓ `ai-types.ts:412` + `service.py:258,276` + `ai-stream.ts:350-355` — `finishReason` 三端契约不一致，合法上游响应让整次生成变"协议错误"且内容不可采纳

- shared 定义**闭合联合**：`finishReason: 'stop' | 'length' | 'aborted'`
- sidecar **原样透传**：`finish = chunk.finish_reason`（`gateway.py:535-537` 只判"是非空字符串"）→ `_sse({"type":"done","finishReason":finish})`
- 渲染进程**严格校验**三值之一，否则 `protocolError('流式响应里有一条不认识的事件')`

OpenAI 兼容协议的合法 `finish_reason` 含 `content_filter`/`tool_calls`（中转还常有 `end_turn`/`stop_sequence`）。该帧是**最后一帧**——用户已看着正文生成完，却拿到"不认识的事件"，`failGen` 把 phase 置 `error`，而可采纳要求 `phase==='ready'` → **全部内容不可采纳**，重试必复现。

**修复**：sidecar 归一化（契约源头在那）：`finishReason` 非 `stop`/`length` 一律落 `"stop"`，`content_filter` 之类转 `error` 事件；shared 注释改为"sidecar 保证只回三个值"，并加共享用例。

### H4 ✓ `window.ts:130-133` — `setWindowOpenHandler` 无协议白名单（与 `will-navigate` 口径不一致）

```ts
win.webContents.setWindowOpenHandler(({ url }) => {
  void shell.openExternal(url);   // ← 无任何校验
  return { action: 'deny' };
});
```

同文件 `will-navigate` 分支是**有**白名单的（`if (isExternalHttpUrl(details.url)) …`），注释还写着"与下面的 setWindowOpenHandler **同一个口径**"——实际不同。`shell.openExternal` 在 Windows 上可触发 `file://`、UNC 路径（`\\host\share` 凭据外泄）、自定义协议（`ms-settings:` 等）。

**当前不可达**（md 白名单把链接降级为纯文本），但 `window.ts:102-104` 自己写了"编辑器早晚要渲染链接"——这个洞是为将来主动打开的。
**修复**：`if (isExternalHttpUrl(url)) void shell.openExternal(url).catch(() => {});`（一行）。

## 4. 已核对无问题的维度（正面结论）

- **路径穿越**：`slugify` 实测 `'..'→'untitled'`、`'../etc'→'..etc'`、`'a\\b'→'ab'`，不构成穿越；章节 path 由 `order:int + 实际目录名` 拼装
- **鉴权**：中间件顺序正确（CORS 最外、业务端点全在鉴权内、仅 `healthz` 豁免）；`compare_digest` 常量时间；"缺失/错误"同响应体
- **token 脱敏**：`JsonFormatter` 是唯一日志出口，`_validation_detail` 刻意丢弃 `input`/`ctx`（否则回显明文 Key 与整章正文）
- **原子写**：同目录 `mkstemp`+`fsync`+`os.replace`，重试耗尽抛 `WriteFailed` 而非静默返回
- **Electron 基线**：`contextIsolation:true` / `nodeIntegration:false` / `sandbox:false`（有实测记录）/ preload 只暴露具名方法不透传 `ipcRenderer`
- **凭据**：`safeStorage` 每次过 `isEncryptionAvailable()`，不可用**明确拒绝存储而非明文降级**；无 `crashReporter`
- **双 pid 杀进程**：Windows venv redirector 处理正确（`taskkill /T /F` 杀进程树）
- **类型与静态检查**：`mypy --strict` 0 错、`eslint` 0 error、无 `any`/无 `!`
- **字数口径**：TS 与 Python 双实现共读 16 例 fixture，覆盖全部分歧码点
- **行尾/BOM（写路径）**：新建内容恒 LF 无 BOM；外部 CRLF 原样往返不污染

> **M3 的两半都值得单记。**
>
> ① **3xx 不是成功。** httpx 默认 `follow_redirects=False`，而这**正是我们想要的** ——
> 跟随重定向会把 `Authorization: Bearer <key>` 发到重定向目标去，一旦 base_url 被填错
> 或被中间件劫持，等于把 Key 交给对方。但"不跟随"就必须"自己判错"：原来的判断是
> `>= 400`，3xx 被放过，于是拿到重定向页的 body —— 它一行 `data:` 都没有，走完空循环
> 发出 `StreamDone("stop")`。**界面显示"生成完成"、正文一个字没有，而记录里也是成功**。
>
> ② **`httpx.InvalidURL` 不继承 `httpx.HTTPError`。** 它的 MRO 是
> `InvalidURL → Exception → BaseException`（0.28.1 实测，`issubclass(...) is False`）。
> 所以三处 `except httpx.HTTPError` 都接不住它 —— 用户把 base_url 填成
> `http://[::1]:not-a-port/v1` 时异常一路逃到 FastAPI，变成一个 500，
> 而它其实是**用户自己能修**的配置错误。修法是把 `InvalidURL` 显式列进 `_HTTPX_ERRORS`；
> 测试里留了一条 `assert not issubclass(...)` 把这个前提钉住（上游改了它会红，
> 那时就能顺手删掉那个冗余项）。
>
> **M4 的两半都关于"这是响应体"。** 异常从这里逃出去不会变成 4xx/5xx（响应头早发出去了），
> 只会让 SSE 流**无声断掉** —— 渲染进程收不到 `done` 也收不到 `error`，只能报一句
> "协议错误"，与真正的原因毫无关联。所以兜底分支自己发一帧 `INTERNAL`。
> 记录那一半更隐蔽：原先只有 `DomainError` 分支会设 `error_code`，于是这类失败在
> `runs.jsonl` 里是 `error: null` —— 一次"用户什么都没拿到"的生成**看起来是成功的**，
> 而这正是审计最不能出现的偏差。`finally` 那处的理由是 Python 语义：
> **`finally` 里抛出的异常会替换正在传播的那一个**，而此刻在传播的可能是
> `CancelledError`（用户点了停止）—— 被换成 `WriteFailed` 之后，上游再也分不清
> "取消"与"磁盘故障"。
>
> **M7 的根因是"约定没被强制执行"。** `repo.py` 的文件头写着"阻塞的文件 IO 一律丢进
> `anyio.to_thread`"，而 `recent` / `remove_recent` 这两个方法是**唯一**没照做的（它们
> 直接读到 `RecentStore`）。而且 `remove_recent` 的写路径还带 `time.sleep` 重试
> （`atomic.py` 的 `_RETRY_DELAYS`，最多 0.3 秒）—— 那是**纯阻塞**的。
> 所以修法不是"在路由里包一层 `to_thread`"（那样下一个新路由还会忘），
> 而是**让 `async` 成为 `WorkRegistry` 的对外承诺**：`recent()` / `remove_recent()`
> 自己丢线程。给"已经在线程池里"的调用方（`app.py::_recent_roots`，它被
> `UsageLedger.today()` 丢进线程）留一个同步的 `recent_entries()`，
> 两个方法并列而不是藏一个私有实现 —— 让"哪个是给事件循环用的"一眼可辨。
> `usage.py::today` 里把注入的 `_roots()` 也丢线程，则是为了让"不阻塞"成为那个类的
> **保证**（注入方换实现也不会把事件循环拖住）。
