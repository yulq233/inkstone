## 4. 会话状态设计

**为什么不用一堆 `useState`**：当前作品、当前章节、打开中、失败原因这四个字段之间有耦合约束（比如"没有作品就不可能有当前章节"）。散装 `useState` 允许出现"作品为 null 但章节非 null"这种非法组合，而它恰好会在切章时序里被读到。用判别联合把非法状态**表示不出来**。

```ts
// features/session/session-reducer.ts

export type SessionState =
  | { kind: 'entry' }
  | { kind: 'opening'; title: string }
  | { kind: 'ready'; work: WorkSummary; chapter: ChapterSummary | null }
  | { kind: 'failed'; work: WorkSummary | null; error: string };

export type SessionAction =
  | { type: 'work/opening'; title: string }
  | { type: 'work/opened'; work: WorkSummary; chapter: ChapterSummary | null }
  | { type: 'work/failed'; error: string }
  | { type: 'work/leave' }
  | { type: 'chapter/selected'; chapter: ChapterSummary };

export function sessionReducer(state: SessionState, action: SessionAction): SessionState;
```

> **实现时的修正（v0.2）**
>
> 1. **`opening` 态不再携带 `WorkSummary`**，改为只带 `title`。打开请求返回**之前**根本拿不到摘要
>    （最近列表项只有 `{rootPath,title,lastOpenedAt,exists}`），硬造一个占位摘要会让后续代码读到假的
>    `chapterCount` / `totalWords` —— 这类"看起来能用"的假数据比缺字段危险。真正需要 `work` 的是
>    `failed` 态（要说明是哪个作品出的错），那里保留。
> 2. **代理绕过常量落在 `packages/shared/src/proxy.ts`**，而不是写在主进程里。主进程要用它拼开关、
>    渲染进程要用它做故障页展示，且放这里才能被单测直接覆盖（主进程模块一 `import` 就会拉起 electron）。
>    同时加了一个 `checkProxyBypassList()` 启动自检 —— 理由是这个开关**失效时没有任何症状**。
> 3. **`AppInfo` 增加 `proxyBypassList` 字段**，由主进程透出实际取值。§6.4 要求故障页展示诊断信息，
>    渲染进程自己拼一份等于没答"实际生效的是什么"。
> 4. **原 `ReadyPanel` 保留为"诊断页"**（入口页右上角「诊断」进入，可返回），而不是删掉。
>    §6.4 的正向/反证验证与 §9 验收 6 都要用它（手动探活、模拟崩溃、看代理绕过）。
> 5. **`WorkShell` 实际是"顶部条 + 两栏"**（左章节侧栏插槽、右内容区插槽），与 §6.1 组件树一致；
>    `03` 文档说的"三栏"里第三栏是顶部条。具体栏宽留到各自步骤再定（§10 风险 1）。

| 动作 | 迁移 | 备注 |
|---|---|---|
| `work/opening` | 任意 → `opening` | 只带 `title`，供界面显示"正在打开《X》" |
| `work/opened` | `opening` → `ready` | `chapter` 传 null 时由 `WorkShell` 自动选第一章（§5.2） |
| `work/failed` | 任意 → `failed` | 保留 `work`，失败页面才能显示是哪个作品出的错 |
| `work/leave` | 任意 → `entry` | 清空章节，**不碰磁盘** |
| `chapter/selected` | `ready` → `ready` | 在非 `ready` 态下收到该动作直接忽略（防御） |

`WorkSessionProvider` 另外暴露一个 `client: ApiClient | null`。它不在 reducer 里 —— 客户端是**外部资源**不是状态：它的生命周期跟着 sidecar 走（§5.4），放进 reducer 会让"重建客户端"变成一次状态迁移，语义上说不通。

## 5. 关键流程

### 5.1 冷启动 → 首页书架

```
sidecar HEALTHY ──► 取连接信息 ──► 建 ApiClient ──► GET /works/recent
                                                          │
                                                  shelfView(items, error)
                                                          │
        ┌───────────────┬──────────────┬─────────────────┴──────────────┐
        ▼               ▼              ▼                                ▼
   items=null      items=null      items=[]                        items 非空
   error=null      error≠null
   → loading       → unavailable   → empty（引导「新建第一本书」）  → ready 卡片墙
```

会话状态保持 `entry`（不自动打开任何作品）。

**读取失败不能吃掉书架**：`useRecentWorks` 允许"成功过一次、之后刷新失败"，即 `items` 与 `error` **可同时非空**。此时书架照常渲染，错误只作为**书架上方的一条提示**＋「重试」按钮出现 —— 若让错误替换书架，用户会以为书库被清空了。

**空书架**：`items.length === 0` 时显示一句"书架还空着。正文会存在你自己选的目录里，不上传。"＋「新建第一本书」；不再并列显示"暂无最近作品"这类空状态噪音文案。

**刻意不自动打开上次的作品**：用户开机点开应用，期待的是"自己选"，而不是被塞进一本三天前写的东西。自动打开也让"打开失败"这条错误路径在启动时就可能触发，噪音大。

### 5.2 新建作品（模态）

```
0. 首页点「＋ 新建作品」（或菜单 作品 → 新建作品）→ 打开 NewWorkDialog
   —— 模态只负责外壳与焦点（打开即聚焦标题框），内容仍是 NewWorkForm
1. 用户填标题（必填）+ 可选作者/题材/字数目标
2. 点「选择目录」→ IPC dialog:pickDirectory（默认路径用最近一次的父目录，存在 localStorage）
3. 校验：标题非空、目录已选
4. POST /works { parentDir, title, author, genre, wordGoal }
5. 200 → sidecar 已建完整骨架（含自动创建的「第一章」）
6. dispatch work/opened { work, chapter: null } → 首页随模态一起卸载
7. WorkShell 挂载 → GET /works/{id}/chapters → 选中第 1 章（order 最小）
```

**模态刻意不支持 Esc / 点背景关闭**：标题与目录是两段不算小的输入，误触背景就丢代价太高；取消只能点「取消」。菜单项的「新建作品」因此只需**打开模态**（聚焦由模态自己的 `useEffect` 负责），不必绕到表单里拿 ref。

第 6、7 步拆开而不是在这里直接选章节：章节列表的获取与选中属于步骤 03 的职责，这一步只保证容器能挂起来。步骤 03 未完成时，`WorkShell` 的侧栏区显示"章节列表将在下一步接入"的占位。

**失败分支**：

| 情况 | 判定依据 | 呈现 |
|---|---|---|
| 目录下已有同名作品 | sidecar 返回 `INVALID_PARAM` | 表单内联报错，保留已填内容 |
| 目录不可写 | `WRITE_FAILED` | 同上，提示换目录 |
| 网络层失败 | `ApiError.isNetwork` | 表单内联报错 + 「重试」按钮（保留输入） |

### 5.3 打开已有作品

```
书架卡片点选 ──► POST /works/open { rootPath }
                      │
        ┌─────────────┴──────────────┐
        ▼                            ▼
  200 → work/opened            WORK_NOT_FOUND
  同时清掉该条 exists=false 标记      │
                                     ▼
                          该卡片就地转灰「目录已移动或删除」
                          + 提供「从列表移除」（DELETE /works/recent）
```

`exists` 由 sidecar 读取时现算，前端不缓存 —— 缓存它会让用户在文件管理器里挪完目录后，界面上仍显示"可用"，点进去才报错。

**卡片状态有严格优先级**：`打开中` > `上次失败的信息` > `目录已移动或删除` > `上次打开 <时间>`。顺序反了，上次的失败信息会盖住这一次的"打开中"。失败信息**按 `rootPath` 认领**，只标出错的那一张卡，不污染整排。

### 5.4 sidecar 状态与客户端重建

```
sidecar 状态        渲染进程行为
────────────────────────────────────────────────────────
BOOTING            显示 StartupOverlay，client = null
HEALTHY            取连接信息 → new ApiClient(conn) → 可用
RESTARTING         显示 StatusBanner，**client 置 null**
FAILED             显示 ErrorPanel
```

**每次 `HEALTHY` 都必须重新 `getConnection()` 并重建 client**。token 不变，但端口变了（sidecar 每次都 `bind :0`）。漏掉这一步的症状是"崩溃自愈之后所有请求打到旧端口，界面永远转圈" —— `03` 文档 §8.3 用加粗标注过这一点，`App.tsx` 里已有实现，这一步把它抽成 `use-api-client.ts` 供后面的组件复用。

```ts
// lib/use-api-client.ts
export function useApiClient(status: SidecarStatus): ApiClient | null;
```

## 6. 代理绕过加固（产品级隐患）

### 6.1 问题

渲染进程的 `fetch` 走 Chromium 网络栈，**会读取系统代理设置**。国内开发机普遍装着本地代理客户端（Clash / v2ray 之类），把系统代理指向 `127.0.0.1:7892`。如果代理规则没有显式放行 loopback，那么：

```
渲染进程 fetch http://127.0.0.1:<port>/api/v1/works/recent
        └──► 被送去 127.0.0.1:7892 代理
                    └──► 代理不认这个请求 → 502 Bad Gateway
```

用户看到的现象是"应用连不上自己的后端"，而排查方向会被引到 sidecar 上（其实 sidecar 一直好好的）。

**这个坑已经在测试侧踩过一次**：`services/sidecar/tests/test_handshake.py` 的 6 个用例曾因此全部返回 502，最后用 `httpx(trust_env=False)` 解决。测试侧修了，产品侧还没修。

### 6.2 方案

主进程启动早期（`app.whenReady()` 之前）显式声明绕过规则：

```ts
// apps/desktop/src/main/index.ts
app.commandLine.appendSwitch('proxy-bypass-list', '<-loopback>;127.0.0.1;localhost');
```

`<-loopback>` 的含义是"**不**对 loopback 使用代理"（前面的 `-` 是取反，这是 Chromium 的既有语法，容易读反）。后面再显式列出 `127.0.0.1` 与 `localhost` 是冗余保险 —— 参数被其他启动器覆盖时仍能兜住。

渲染进程侧只做读取与断言，不重复配置：

```ts
// lib/app-proxy.ts
/** 读回诊断信息，只用于日志与故障页展示，不参与业务判断 */
export function describeProxyBypass(): string;
```

### 6.3 为什么不用 `session.setProxy`

`session.setProxy` 是异步的，且必须在窗口加载**之前**完成，否则第一次请求仍会走错路径 —— 而它返回的 Promise 与窗口创建之间存在竞态。命令行开关在进程启动时就生效，没有这个窗口期。

### 6.4 验证方式

| 方式 | 步骤 |
|---|---|
| 手工（必须做） | 打开系统代理，把代理指向一个不存在的端口，启动应用 —— 入口页仍能拉到最近列表 |
| 反证 | 临时把 bypass 开关去掉，同样条件下请求应失败（证明开关确实起作用，不是碰巧） |
| 日志 | 故障页展示 `describeProxyBypass()` 的结果，用户报障时能一眼看出是不是代理问题 |

## 7. 异常与边界

| 场景 | 行为 |
|---|---|
| 书架为空 | 显示一句说明 +「新建第一本书」（点了直接开模态）；不叠加"暂无最近作品"这类空状态文案（省掉一行噪音） |
| 书架读取失败且**从没读到过** | 不渲染书架，显示"书架读取失败：…"＋「重试」 |
| 书架**刷新**失败但已有数据 | 错误作为书架**上方**的提示 ＋「重试」按钮，**不替换书架**（替换会被误读成"书库被清空"） |
| 书架项 `exists=false` | 卡片灰态 + 红字标注 +「从列表移除」；**不自动清理**（用户可能只是把目录挪到了别处，回头还要用） |
| 卡片状态优先级 | `打开中` > 上次失败 > `!exists` > 上次打开时间；失败信息按 `rootPath` 认领，只标出错的那张 |
| 打开过程中 sidecar 崩了 | 请求以网络错误收尾，进入 `failed` 态并写明原因，提供「返回作品入口」；**不做自动重试**。会话状态活在 Provider 里（恒挂载），但不会替用户重发请求 |
| 401 | 直接进 `ErrorPanel`（token 失效是 bug 或应用被外部重启，重试无意义） |
| 同一次会话里重复点「新建」 | 提交中禁用按钮（本地 `submitting` 状态），不依赖后端去重 |
| 作品路径含中文与空格 | 一律 `encodeURIComponent`；`02` 文档 §6.5 要求测试覆盖，入口页的手工验收里加一条 |

## 10. 风险

| 风险 | 对策 |

| 容器形状定错，后续步骤返工 | 三栏布局只定**骨架与插槽**，不给侧栏/编辑器内部的尺寸约束；它们的布局细节归各自步骤 |

## 11. v0.3 变更：入口页 → 首页书架（**超出本文档原设计**）

> 日期 2026-09-23 ｜ 触发：用户反馈"我没找到使用 AI 写作的地方，并且能否增加一个首页，首页是个书架，存放正在写的作品，不要直接就是创作作品的输入框"

原文（§1.1、§3、§5.1、§5.2）写的是**入口页常驻新建表单 + 最近列表**。全部 docs 里 grep「书架 / 首页 / 封面」**零命中**，所以这是**超出设计**的改动。此处回写，避免文档与代码打架。

| 项 | 原文 | 现在 |
|---|---|---|
| 首页主体 | 常驻新建表单 + 最近列表 | **书架卡片墙**占主区；新建 / 从文件夹打开降为两个按钮 |
| 列表组件命名 | `RecentWorkList.tsx` | `WorkShelf.tsx`（**旧文件已删除**） |
| 新建 | 常驻表单 | `NewWorkDialog.tsx` 模态包裹 `NewWorkForm.tsx` |
| 书架状态判定 | 散在 JSX 里 | 抽成纯逻辑 `shelf-view.ts`（可单测，只 type-only import，不拖进 UI 链） |
| 数据源 | `RecentWork` | **不变** —— 未新增任何端点 |

**刻意不做的**：卡片上不显示「章节数 / 总字数」。`RecentWork` 只有 `{rootPath, title, lastOpenedAt, exists}`；这两个数在 `WorkSummary` 上（需作品先被打开注册），对未打开的作品要给每个 `manuscript/` 重扫一遍 —— 新端点 + N 倍 I/O。用户明确选择"先只做前端"，留待后续。

**顺手修的既有隐患**：`.modal-backdrop` / `.modal` 原本只定义在 `features/editor/editor.css`，首页能用上只是因为 `App → WorkShell → EditorPane` 是**静态** import 链 —— 一旦有人把编辑器改成 `lazy()`，模态背景会**静默消失**。已把这两个基元上移到 `global.css`。

**仍未做的**（用户另一项诉求）：渲染进程目前只有设置里的「AI 模型」页（列模型 + 测连接），编辑器里**没有任何 AI 入口**。"用 AI 写作" = `docs/11` 的 **P1**（续写 + 幽灵文本），尚未实现。
