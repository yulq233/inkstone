## 0. 为什么这一步单独成篇

`03` 文档在 §6.5 开头写了一句加粗的话：

> **第 1~3 步是这个功能的全部价值**。跳过 flush 直接切换，就是"偶发丢字"这类最难查的 bug 的来源。

切章这个动作看起来只是"换一份内容显示"，实际它同时在做四件事：**把旧章的未落盘内容救出来、判断能不能切、换掉编辑器的内容与基准 hash、清掉上一章的状态残留**。少做任何一件，用户就会在某次切换后发现自己少了几百字，而且**复现不了**。

所以这一步的重点不是侧栏 UI，是那个时序。

## 4. 侧栏设计

### 4.1 列表项

```
┌───────────────────────────────────────┐
│ 第 3 章 · 夜行             1,842 字   │  ← 当前章：左侧竖条 + 背景高亮
│ （状态图标）                           │
└───────────────────────────────────────┘
```

| 元素 | 来源 | 说明 |
|---|---|---|
| 序号 | `order` | 从 1 开始；重排后这个值会变而 `id` 不变 |
| 标题 | `title` | 取自正文首个 ATX 标题行；没有标题行时后端给占位文字 |
| 字数 | `wordCount` | **列表项自带，不需要额外请求** |
| 状态 | `status` | `draft` / `revising` / `done`，用一个小圆点着色（不用文字，省横向空间） |
| 高亮 | 与 `currentChapter.id` 比对 | 用 `id` 不用 `order`：重排后 `order` 会变 |

### 4.2 列表的刷新时机

| 时机 | 做法 | 理由 |
|---|---|---|
| 进入作品 | `listChapters(workId)` | 首次加载 |
| **保存成功后** | **本地更新**该项的 `wordCount` | `SaveOutcome` 里已经有 `wordCount`（服务端写入时算好的），直接用它替换列表里那一项。零请求、实时、不闪 |
| 新建章节后 | `listChapters(workId)` | 需要拿到新章的 `id` 与目录名 |
| 切章时 | **不刷新** | 字数已由上一行的本地更新覆盖；刷新会让长列表闪一下 |
| 外部新增了 md 文件 | 用户手动触发（侧栏顶部的刷新按钮） | M0 不做文件监听（`02` 文档 §2.4 的决策），给一个显式入口 |

「保存成功后本地更新字数」是个小设计但很关键：如果每次保存完都重新拉列表，用户会看到侧栏在打字过程中反复闪动；如果完全不更新，用户又看不到进度。本地更新两头都躲开了。

### 4.3 空态

正常情况不会出现（新建作品时后端已自动建「第一章」）。只在两种情况下出现：

- 用户手工删掉了所有章节目录（外部操作）
- 作品是在旧版本里创建的、结构不全

此时显示一句"这部作品还没有章节" + 「新建章节」按钮。**不自动补建** —— 静默往用户的作品里塞文件是不礼貌的。

### 4.4 滚动与键盘

- 切换章节后，侧栏自动滚动使当前项可见（`scrollIntoView({ block: 'nearest' })`，用 `nearest` 避免整列表跳动）
- `↑` / `↓` 在侧栏聚焦时切上一章 / 下一章；`Mod+N` 新建章节（快捷键在步骤 06 的菜单里统一注册，本步骤只保证有对应的处理函数）

## 5. 切章时序（本步骤的核心）

### 5.1 完整时序

```
用户点击章节 B
  │
  ├─ 1. if (autosave.hasUnsavedChanges()) { ok = await autosave.flush() }
  │        └─ flush() 返回 false ⇒ 内容没落盘
  │              ├─ state==='error'    ⇒ 中断，顶部提示「当前章节保存失败，已阻止切换」+「重试」
  │              └─ state==='conflict' ⇒ 中断，打开 ConflictDialog
  │
  ├─ 2. if (autosave.getState() === 'conflict') ⇒ 中断（同上，flush 已返回 false，这里是双保险）
  │
  ├─ 3. const token = ++switchToken          // 竞态防护，见 §5.3
  │
  ├─ 4. setSwitching(true)                    // 编辑器显示加载遮罩，侧栏保持可点
  │
  ├─ 5. const content = await client.readChapter(workId, B.id)
  │        └─ 失败 ⇒ 中断，提示错误，保持在原章节（原章节内容仍在编辑器里，未被破坏）
  │
  ├─ 6. if (token !== switchToken) return      // 已被更新的点击取代，丢弃本次结果
  │
  ├─ 7. const { warnings } = editorHandle.setMarkdown(content.markdown)
  │        └─ setContent(doc, { emitUpdate: false })   ← 不触发 onChange（见步骤 02 坑 #1）
  │
  ├─ 8. dispatch({ type: 'chapter/selected', chapter: content })
  │        └─ chapter.id 变化 ⇒ useAutosave 重建实例，新实例 baseHash = content.hash
  │
  ├─ 9. editorHandle.focusStart()
  │
  └─ 10. setWarnings(warnings); setSwitching(false)
```

### 5.2 与 `03` 文档 §6.5 的两处对应关系

| `03` §6.5 | 本步骤的落地 | 差异原因 |
|---|---|---|
| 第 8 步 `currentChapter = B; autosave.reset(hash)` | `dispatch(chapter/selected)` → **实例重建** | 步骤 03 的决策是"生命周期 = 章节生命周期"，重建比复用再 `reset` 更不容易漏状态。`reset(hash)` 保留给"同章内重载"（冲突选「用磁盘版本」） |
| 第 7 步 `setContent(doc, false)` | `setContent(doc, { emitUpdate: false })` | 前者是 TipTap **v2** 的签名；v3 的第二个参数是 options 对象，传 `false` 会被忽略、`emitUpdate` 取默认值 `true` —— 后果是切章即触发一次保存、且用的是**旧 baseHash**，弹出假冲突。已在步骤 02 §2 实测确认 |

第 7、8 步在同一个批次里执行（React 的批处理），不会出现"内容已换、身份未换"的中间态被观察到。

### 5.3 竞态防护：为什么是 token 而不是禁用点击

快速翻章是真实使用场景（找一段话时会连点好几章）。两种做法：

| 做法 | 问题 |
|---|---|
| 切章期间禁用侧栏 | 用户连点时后几次点击被吞掉，感觉"卡" |
| **递增 token，丢弃过期响应** | 每次点击都生效，最后一次赢 |

选后者。实现要点：

```ts
const switchToken = useRef(0);

async function switchTo(target: ChapterSummary) {
  const token = ++switchToken.current;
  // ... 各 await 之后都插一句：
  if (token !== switchToken.current) return;
}
```

**每个 `await` 之后都要检查**，而不是只在最后一次。特别是第 5 步的 `readChapter` —— 它可能耗时较长（大章节），期间用户点了第三次，那么这次的结果必须丢弃，否则会把用户拉回到中间那次点击的章节。

第 7 步（`setMarkdown`）执行前必须再查一次 token：一旦过期就**不要动编辑器** —— 此时编辑器可能已经被更新的那次切章写入了内容，再覆盖一次会把它的结果冲掉。

### 5.4 flush 返回值的处理

`Autosave.flush()` 已经按这个需求设计成返回 `boolean`（`true` = 无未保存内容）。**必须检查返回值**：

```ts
const ok = await autosave.flush();
if (!ok) {
  // 不能切。用哪种提示取决于状态：
  //   error    -> 顶部红色条 +「重试」
  //   conflict -> 打开 ConflictDialog
  return;
}
```

`flush()` 内部是"循环 + 串行闸门"，会等到"当前这批 + 期间新到的补偿批"全部落盘才返回 true。这不是保守写法 —— 它的注释说明了：`runLoop` 退出与 promise settle 之间隔着微任务，那一瞬间仍可能有新改动进来，只 await 一次会漏掉这批内容，而调用方紧接着就会重建实例，那批字就真没了。

## 6. 新建章节

```
点「新建章节」
  └─ const chapter = await client.createChapter(workId, { title: `第 N 章` })
       ├─ 刷新列表（listChapters）
       ├─ 选中新章（走 §5 的时序 —— 注意：此时也要先 flush 当前章！）
       └─ 焦点落在文首，等待用户改名（标题取自正文首行）
```

**坑**：新建章节也是"切换"，所以**同样要先 flush 当前章**。容易漏，因为它看起来是"加东西"不是"换东西"。实现上让"新建"走 `switchTo(新章)` 的同一条路径，而不是另写一遍。

标题的默认值：请求体里带一个占位标题（如 `第 5 章`），服务端会用它生成目录名，正文首行写入 `# 第 5 章`。用户随后在正文里改标题，保存时服务端会从首行同步 `title`（已有测试覆盖：`test_write_updates_title_from_first_line`）。

## 7. 异常与边界

| 场景 | 行为 |
|---|---|
| `readChapter` 失败 | 中断切换，**保持在原章节**。原章节内容仍在编辑器里，不被破坏 —— 这是"失败要退回安全态"而不是"进入半截状态" |
| 切章过程中 sidecar 挂了 | 同上；顶部显示服务状态条（步骤 01 的 StatusBanner 已接管） |
| 切章时当前章处于 conflict | 中断，打开对话框。`flush()` 在 conflict 态直接返回 false |
| 切到已经在看的章节 | 直接 return（比对 `id`），不做任何动作 —— 否则会白白 flush 一次并重建编辑器内容，把光标弄没 |
| 大章节（10 万字）读取慢 | 显示加载遮罩；不阻塞侧栏点击（token 机制保证最后点击赢） |
| 列表里某项的目录被外部删了 | `readChapter` 返回 `CHAPTER_NOT_FOUND` → 中断 + 提示 + 触发一次列表刷新 |
| 章节数为 0 时点新建 | 正常创建（后端会分配 `order=1`） |

## 8. 测试设计

切章时序是纯逻辑，可以脱离 DOM 测 —— 把它写成不依赖 React 的类/函数，或者用一个小的状态机对象：

| 用例 | 说明 |
|---|---|
| **flush 失败时中断** | 假 `Autosave` 返回 false → 断言没有调用 `readChapter`（这是最关键的回归测试） |
| flush 成功 → 继续 | 断言调用顺序：`flush` → `readChapter` → `setMarkdown` → `dispatch` |
| `readChapter` 失败 → 保持原章 | 断言 `dispatch` **未**被调用 |
| **连点两次，第一次的响应丢弃** | 让第一次 `readChapter` 的 promise 后 resolve，断言 `setMarkdown` 只被调用一次（用第二次的结果） |
| 切到当前章 → 无动作 | 断言 `flush` 未被调用 |
| 新建章节走同一条路径 | 断言新建后也调用了 flush |
| 保存成功后列表项字数被本地更新 | 断言列表状态里对应项 `wordCount` 变化且没有新的 `listChapters` 调用 |

侧栏组件的渲染不做 DOM 测试（同步骤 02 的约定），走手工验收。

## 9. 验收标准（A3）

**A3 原文**：连续写 3 章、每章 2000 字以上，切换章节不丢内容 —— 三轮往返切换后逐字比对。

| # | 步骤 | 判定 |
|---|---|---|
| 1 | 第 1 章写 2000+ 字，立刻点第 2 章 | 内容不丢 |
| 2 | 第 2 章写 2000+ 字，立刻点第 3 章 | 内容不丢 |
| 3 | 第 3 章写 2000+ 字，立刻点回第 1 章 | 第 1 章内容与写入时逐字一致 |
| 4 | 三轮往返后再回第 2、3 章 | 三章都与写入时一致 |
| 5 | **每次切章前都不停顿**（在防抖 500ms 内就切） | 这一步专门验 flush 真的生效 —— 停顿等待反而会掩盖问题 |
| 6 | 断网/停掉 sidecar 后切章 | 被拦下并提示，**不是静默丢弃** |
| 7 | 快速连点 5 次不同章节 | 最终停在第 5 次点的章节，且中间章节的内容都完好（token 机制） |
| 8 | 用外部编辑器逐字节比对三个 `chapter.md` | 与界面显示一致，无多余空行、无 CRLF |

第 5 项是 A3 的真正考点。停顿再切章，`Autosave` 的防抖已经落盘了，测不出 flush 有没有接线。

## 10. 风险

| 风险 | 对策 |
|---|---|
| 漏掉 flush 或漏检查返回值 | 这是全项目最贵的 bug。测试用例 1 专门锁它；代码里 `flush()` 的返回值是 `boolean` 而非 `void`，类型系统会提醒 |
| `token` 检查只写了一处 | §5.3 明确要求"每个 await 之后都查"，测试用例 4 用乱序 resolve 覆盖 |
| 列表字数本地更新写错项（按 order 而非 id 匹配） | 一律按 `id` 匹配；重排后 `order` 会变 |
| 新建章节忘了 flush | 让"新建"复用 `switchTo` 的同一条代码路径，而不是复制一遍逻辑 |
| React 18/19 的批处理让"内容已换、身份未换"的中间态被渲染 | 第 7、8 步在同一事件处理器内同步调用，React 会合并为一次渲染；不做 `await`，避免拆成两次渲染 |

## 11. 实现偏差与补充（v0.2）

设计文档与代码冲突时，**以本节为准**。

### 11.1 正文不进会话 reducer：`content` 由 `WorkShell` 持有

v0.1 §3 让 `chapter/selected` 携带完整 `ChapterContent`。实现时改成：

- 会话 reducer 只记**身份**：`{ type: 'chapter/selected'; chapter: ChapterSummary }`（`session-reducer.ts:34`）；
- 正文 `ChapterContent` 由 `WorkShell` 的 `useState<ChapterContent | null>` 持有（`WorkShell.tsx:50`）。

理由：正文是**页面的数据**，不是**应用的会话身份**。它每次切章都整块换掉，塞进 reducer 会让
`session-reducer` 的单测全部要跟着改，而 reducer 本身并不需要理解正文。

配套约束：`apply(summary, content)` 一次调用同时写两处（`WorkShell.tsx:151-156`），
同步执行、不 `await`，所以 React 合并成一次渲染 —— §10 最后一行担心的中间态依然不存在。

### 11.2 时序抽成纯函数 `runChapterSwitch`

渲染进程的 vitest 环境是 `node`（`vitest.config.mts` 写明的取舍：没有 jsdom、没有
`@testing-library`），挂在 React 钩子里的时序**一行都测不到**。而本步骤最贵的 bug
（漏 flush → 偶发丢字）恰恰只能靠测试锁住。

所以时序落在 `chapter-switch.ts` 的 `runChapterSwitch(deps, target)`：入参是
`hasUnsavedChanges` / `flush` / `saveState` / `readChapter` / `guard` / `apply` 等几个函数，
返回一个 `SwitchOutcome` 联合类型。`use-chapter-switch.ts` 只剩"把 outcome 映射成 React 状态"，
**不含任何需要小心写的分支**。

### 11.3 `flush()` 抛异常时收敛成 `blocked-save`

`Autosave.flush()` 正常不抛（内部已按错误码分类），但调用方是 `void switchTo(...)`，
接不住 rejection —— 万一抛出就是个未处理的 promise，症状是"点了切章，毫无反应"。

`runChapterSwitch` 用 try/catch 包住 flush，异常一律当"没落盘"处理（`chapter-switch.ts:93-110`）。
**绝不放行**：不确定有没有落盘时，保守比激进安全。

### 11.4 `getAutosave` 惰性取值函数打破循环依赖

`useChapterSwitch` 需要 `Autosave`（为了 flush），`useAutosave` 需要 `content`
（`useChapterSwitch` 的输出）。直接互传实例在 JS 里是循环依赖。

解法：`useChapterSwitch` 收 `getAutosave: () => Autosave | null`（**取值函数不是实例**），
`WorkShell` 用 `autosaveRef` + effect 同步（`WorkShell.tsx:55/77/93-95`）；
反方向用稳定的 `applyWordCount` 回调接通。

顺带语义更准：`Autosave` 实例每次换章都会被换掉（步骤 03 的"生命周期 = 章节生命周期"），
传实例会让钩子持有过期的那一个，取值函数则总是拿到当下的。

### 11.5 `ConflictResolution` 增加可空的 `wordCount`

§4.2 说"保存成功用 `SaveOutcome.wordCount` 本地更新列表"。但**解决冲突**这条路径的
`wordCount` 来源不同：选「用磁盘版本」时字数写在 409 信封里、由服务端算好；选「保留我的」
之后还要再写一次盘。所以：

- `ConflictResolution.wordCount: number | null` —— `null` 表示**客户端不该自行推算**，
  等下一次写入的回执再更新（`conflict-actions.ts`）；
- `useAutosave` 的 `onSaved(chapterId, wordCount)` 只在 `wordCount !== null` 时调用
  （`use-autosave.ts`）。

### 11.6 显示文案：`chapterLabel` 而不是 `displayChapterTitle`

`chapterLabel(chapter): { text, muted }`（`chapter-list.ts`）。三种"标题不值得单独显示"
的情况合并成同一种处理，都退回只显示序号并置 `muted: true`：

| 情况 | 处理 |
|---|---|
| 空标题 / 纯空白 | 只显示「第 N 章」 |
| 服务端回退值「未命名」 | 同上（`TITLE_FALLBACK` 与 `domain/chapter.py` 对齐） |
| 标题恰好是 `第 N 章`（新章占位，§6） | 同上 —— 否则显示成「第 3 章 · 第 3 章」 |

`muted` 由 `ChapterListItem.tsx` 映射成次要色。

### 11.7 侧栏列表自成一体

`ChapterSidebar` 自己渲染头部（刷新 / 新建）、列表、空态、加载态、错误态；
`WorkShell` 只传数据与回调。v0.1 §3 让 `WorkShell` 直接拼装，实现时收敛进组件，
避免 `WorkShell` 继续膨胀。

### 11.8 切章期间用遮罩挡输入，而不是禁用侧栏

§5.3 的决策"不禁用点击"指的是**侧栏**（禁用会把后几次点击吞掉，用户感觉是卡）。
但**编辑器**必须挡：读正文期间用户还在往旧章里打字的话，`apply` 一到
这些字就跟着 `content` 一起被换掉。

做法是 `EditorPane` 的 `switching` 遮罩（半透明 + 挡指针），且只在 `onProceed`
之后出现 —— 被挡下的切换**不会闪一下遮罩**（`chapter-switch.ts:57-61`）。

### 11.9 被拦下时给一句人话（`shell-notice`）

`blocked-save` / `failed` 都落到 `WorkShell` 的 `shell-notice`：
`blocked-save` 提示"请先点状态栏的「重试」"；`failed` 提示"切换到「X」失败：<原因>"，
且 `missing` 时顺手 `load(true)` 刷新列表，让侧栏不再显示一个已被外部删掉的项。

`blocked-conflict` 不开 notice，直接打开冲突对话框（`onBlockedByConflict`）。

### 11.10 `load()` 里"清空"和"保留"必须分开（`docs/13` M21）

原实现只有一句：

```ts
if (current.client === null || current.workId === null) { setChapters([]); … }
```

`client` 为 null 有**两种**成因，行为却必须相反：

| 成因 | 该做什么 |
|---|---|
| 没打开作品（`workId === null`） | **清空** —— 上一部作品的列表不该漏给下一个 |
| 开着作品、sidecar 暂时不在 | **保留** —— 绝不能清 |

第二种是常态而非异常：sidecar 崩溃自愈时端口会变（每次 `bind 127.0.0.1:0`），
所以 `useApiClient` 必须先把 `client` 置 null、拿到新连接信息后再重建。
两步之间只隔一次异步取连接信息，但足够让"重新拉列表"的 effect 跑一遍 ——
那一遍若清空，侧栏会瞬间变成「这部作品还没有章节。」外加一个「新建章节」按钮。
用户的第一反应是**稿子被删了**，而不是"服务在重启"。

判据因此改成**作品身份**：`chapter-list.ts::decideChapterListAction(workId, hasClient)`
返回 `clear` / `keep` / `fetch` 三态，`keep` 那一档只收掉 `listLoading`
（上一轮请求若正卡在半路，`finally` 里因为 token 过期不再兜底），
`chapters` 与 `listError` 一律不动，等重连后那次 effect 再刷新。

抽成纯函数的理由同 §11.2：症状是"列表闪空"，而它由钩子里的状态迁移造成，
node 环境（无 jsdom）测不到迁移 —— 抽出来才能钉住（`test/chapter-list-action.test.ts`）。

### 11.11 遮罩的收起责任用**计数**，不是"最新那次"（`docs/13` M23）

`switchTo` 里原来写的是：

```ts
if (outcome.kind === 'superseded') return;   // ← 早退
if (proceeded) setSwitching(false);
```

意图是"被取代时什么都不做，遮罩归更新的那次管"。但**更新的那次不一定 proceed**：
`SwitchOutcome` 里有一半种类根本没走到 `onProceed`（`ignored`＝点的就是当前章、
`blocked-save` / `blocked-conflict`＝旧章没落盘）。于是这个序列就能把界面卡死：

1. 点章 A（大章节，读得慢）→ `onProceed` → 遮罩出现；
2. 等得不耐烦，点回**自己原来那章**想取消 → `ignored`，没开过遮罩，也不会关；
3. A 回来发现 token 过期 → `superseded` → 早退，也不关。

两次都没人收，遮罩永久盖在编辑器上，只能重启。

改为 `switching-counter.ts` 的**在飞计数**：`onProceed` 里 `+1`，函数返回时
**无条件** `release()`（在 `superseded` 判断**之前**），归零才回调 `setSwitching(false)`。
责任从"最新那次"变成结构性的 —— 谁离场时归零谁负责。两个边界：`release` 挡住下溢
（负数会让下次 `acquire` 落在 0 之外，遮罩再也收不齐）；换作品的 effect 调 `reset()`
（不回调），在飞那几次迟到的 `release` 会被 `pending === 0` 的守卫忽略。

同样的取舍在第 3 批出现过一次（`docs/13` M18 的 `seqRef`），但那里判的是
"**这次结果还能不能落地**"，这里判的是"**还有没有人占着遮罩**" —— 一个是身份，一个是计数，
不能共用同一个变量。
