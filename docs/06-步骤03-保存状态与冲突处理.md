## 0. 为什么这一步排在切章之前

原计划把"切章"排在"保存"前面（`02` 文档的批次划分是按 WS 编号走的）。实际依赖是反的：

```
切章时序第 1 步 = await autosave.flush()      ← 依赖保存能力
```

先做切章会得到一个"没有 flush 可调"的假切章，还得为它编一个临时接口，等保存做完再拆掉 —— 纯返工。所以调整顺序为 **编辑器 → 保存 → 切章**，每一步只依赖前一步。

调整后的好处是验收也变顺了：本步骤做完就能单独验 A4（强杀不丢字），不需要切章功能配合。

## 4. 接线设计

### 4.1 实例生命周期 = 当前章节的生命周期

```ts
// features/editor/use-autosave.ts
export interface UseAutosaveInput {
  client: ApiClient;
  workId: string;
  chapter: ChapterContent;        // 载入章节时拿到的对象，hash 从这里来
  getMarkdown: () => string;      // 来自 EditorHandle（步骤 02）
  onWarnings: (w: AdapterWarning[]) => void;
}

export interface UseAutosaveResult {
  state: SaveState;
  conflict: ExternalModifiedDetail | null;
  error: string | null;
  retry: () => void;
  resolveConflict: (choice: ConflictChoice) => Promise<void>;
  /** 供切章（步骤 04）与关窗前调用 */
  handle: Autosave;
}

export function useAutosave(input: UseAutosaveInput): UseAutosaveResult;
```

**每次 `chapter.id` 变化就重建实例**（`useEffect` 的依赖是 `chapter.id`，return 里 `dispose()`）。**不要复用实例再 `reset(hash)`** —— 复用会让"上一章的 `mustSave` / `pendingSince` 状态"有机会漏进来，而这个漏进来的代价是往新章节里写旧章的内容。重建是更安全的默认。

`reset(hash)` 留给步骤 04 在"同一章内重载"的场景用（比如冲突选了"用磁盘版本"）。

### 4.2 三个出口的接线

```ts
const save = async ({ markdown, baseHash }: { markdown: string; baseHash: string }) => {
  const res = await client.writeChapter(workId, chapter.id, { markdown, baseHash });
  if (res.backupPath !== null) notifyBackupCreated(res.backupPath);   // 见 §5
  return res;                                                          // { hash, wordCount, savedAt }
};

new Autosave({
  getMarkdown,                    // 每次保存都现取，保证写的是最新内容
  save,
  baseHash: chapter.hash,
  onStateChange: setState,
  onConflict: (detail) => setConflict(detail),
  onError: (err) => setError(describeApiError(err)),
});
```

`getMarkdown` 每次都重新取（`Autosave` 就是按这个契约设计的："每次保存都重新取，才能保证写的是最新内容"）。`save` 里**不做任何重试** —— `api.ts` 顶部注释已写明：写操作绝不重试，幂等性由 `baseHash` 保证，重试反而会拿旧 hash 撞 409。

## 5. 状态指示（六态 → 四种说法）

`Autosave` 内部有 6 个状态，但用户只该看到 4 种。多出来的两个是内部实现细节。

| 内部状态 | 界面文案 | 颜色 | 说明 |
|---|---|---|---|
| `idle` | 已保存 | 次要色 | 刚载入，尚无改动 |
| `saved` | 已保存 | 次要色 | 显示"最后保存时间"（`savedAt`），相对时间（"刚刚" / "3 分钟前"） |
| `dirty` | **未保存** | 警示色 | 只在 `dirty` 持续超过 1 秒后显示 —— 500ms 的防抖窗口内一闪而过的"未保存"是噪音 |
| `saving` | 保存中 | 次要色 | 带细进度指示（三点动画或细线） |
| `error` | **保存失败，内容仍在编辑器里** | 危险色 | 配「重试」按钮。文案要点：**明确告诉用户字没丢**，否则第一反应是恐慌 |
| `conflict` | **文件被外部修改** | 危险色 | 点击打开 `ConflictDialog`。此时 `Autosave` 已停止自动保存（`onChange` 在 conflict 态直接 return） |

补充规则：

- `dirty` 的延迟显示用**定时器**实现，不能在渲染里判"距上次改动的毫秒数"（那会不停重渲染）
- 状态指示永远可见（不隐藏），它是用户对"我的稿子在不在"的唯一依据
- **备份提示**：`backupPath !== null` 时（说明发生过覆盖），显示一次性提示「磁盘上的旧版本已备份到 .inkstone/backups/」。这条不常出现，但出现时用户需要知道去哪找

## 6. 冲突处理（409）

### 6.1 触发链

```
Autosave.attemptSave ──► ApiError.isConflict ──► setState('conflict')
                                              └─► onConflict(detail) ──► ConflictDialog
```

`detail` 可能为 `null`（信封形状不对时 `Autosave` 刻意给 null，见其注释）。此时对话框退化成"只说明有冲突"，三个选项里**只保留「用磁盘版本重载」与「另存副本」**，不提供"覆盖" —— 覆盖需要 `diskHash` 当 `baseHash`，没有 detail 就没有这个值。这是"宁可少给一个选项，也不做可能盖错的事"。

### 6.2 三选一

```ts
export type ConflictChoice = 'use-disk' | 'keep-mine' | 'save-as-copy';
```

| 选项 | 步骤 | hash 收尾 |
|---|---|---|
| **a. 用磁盘版本** | `setMarkdown(detail.diskMarkdown)` → 清空编辑器里的本地改动 | `autosave.resolve(detail.diskHash)` |
| **b. 保留我的并覆盖** | ①`client.writeChapter(workId, id, { markdown: 我的, baseHash: detail.diskHash, backup: true })` ②成功后用返回的 `hash` 收尾 | `autosave.resolve(res.hash)` |
| **c. 另存副本** | ①`client.createChapter(workId, { title: 原标题 + '-副本' })` ②`client.writeChapter(workId, 新章 id, { markdown: 我的, baseHash: 新章的 hash })` ③当前章按 a 的路径重载磁盘版本 | `autosave.resolve(detail.diskHash)` |

**b 为什么不走 `Autosave.save`**：实例的 `baseHash` 是冲突前的旧值，用它写必然再撞 409。这条路必须绕开状态机直接调 API，成功后再 `resolve(新 hash)` 把状态机拉回来。`Autosave.resolve` 的注释写明了它的语义："无论用户选了哪条路，解决完之后基准都是磁盘当前版本"。

**c 的顺序不能反**：必须**先**把副本写成功，**再**重载当前章。反过来的话，一旦写副本失败，用户的选择就落空了 —— 当前章已经变成磁盘版本，而他的内容没了。

### 6.3 对话框内容

并列展示两版（M0 简化版，不做行级高亮）：

| 栏位 | 内容 |
|---|---|
| 左 | 「你的版本」+ 字数 + 前 400 字预览 |
| 右 | 「磁盘上的版本」+ `diskSavedAt` + 字数 + 前 400 字预览 |
| 底部 | 三个按钮 + 一句后果说明（选"覆盖"时必须写"磁盘版本会先备份"） |

**不做行级 diff** 的理由（`03` 文档 §11）：M0 做简化版能覆盖 90% 的判断需求，行级高亮要与版本功能一起做才有价值。

## 7. 关窗前 flush（需要主进程配合）

### 7.1 问题

`Autosave` 有 `maxWait 3000ms`，也就是说**任何时刻都可能存在最多 3 秒的未落盘内容**。用户点窗口关闭按钮时，如果直接关，这 3 秒就丢了。这正是 A4 要防的事，而 A4 的判定标准写的是"强杀进程后丢失 ≤ 3 秒" —— **正常关闭应该做到 0 丢失**（强杀才允许丢 3 秒）。

### 7.2 时序

主进程持有窗口，渲染进程持有内容，所以必须来回一次：

```
用户点关闭
  │
  ▼
主进程 win.on('close') ──── e.preventDefault() 拦下
  │
  ├─► webContents.send('app:beforeQuit')
  │        │
  │        ▼
  │   渲染进程：await autosave.flush()
  │        │
  │        ├─ 落盘成功 ──► send('app:flushResult', { ok: true })
  │        └─ 仍有未存 ──► send('app:flushResult', { ok: false, reason })
  │
  ▼
主进程收到结果
  ├─ ok:true  ──► win.destroy()  → 继续退出流程（关 sidecar）
  ├─ ok:false ──► 弹原生对话框：「有内容尚未保存，仍要退出？」[取消] [强制退出]
  └─ 3 秒无响应 ──► 视为卡死，直接 destroy（绝不允许"关不掉"）
```

### 7.3 三条硬规则

1. **必须有超时**。`flush` 依赖 sidecar；sidecar 挂了时会走 `ApiError.isNetwork` 的失败路径。缺超时的话应用会**关不掉**，这比丢字更让用户愤怒。
2. **顺序不能反**：先 flush，再关 sidecar。反了的话 flush 必然失败（服务已经没了），变成"每次都提示有未保存内容"。
3. **`app:beforeQuit` 只发一次**。主进程要置一个 `quitRequested` 标志位 —— `close` 事件在 `destroy()` 之前可能被触发多次，重复发会让渲染进程 flush 两遍（第二遍是无害的空转，但会拖慢关闭）。

### 7.4 IPC 契约（同步补回 `02` 文档 §5.3）

| 通道 | 方向 | 载荷 |
|---|---|---|
| `app:beforeQuit` | 主 → 渲染 | 无 |
| `app:flushResult` | 渲染 → 主 | `{ ok: boolean; reason?: string }` |

## 8. 异常与边界

| 场景 | 行为 |
|---|---|
| 保存失败后用户继续打字 | **允许**。`Autosave` 会置 `mustSave=true` 并进入 `error`；用户点「重试」时写的是最新的内容（`getMarkdown` 现取） |
| 保存失败后切章 | 步骤 04 会拦（`flush()` 返回 false → 中断切换） |
| 网络失败但 sidecar 还活着（端口变了） | 显示"本地服务无响应" + 「重试」。主进程的 supervisor 会自动重启 sidecar，重启后渲染进程重建 client（步骤 01 的 `useApiClient`），此时重试就能成功 |
| 401 | 提示"本地服务鉴权失效，请重启应用"，不提供重试 |
| 冲突发生时用户正在打字 | `Autosave` 在 conflict 态下 `onChange` 直接 return，不丢内容但也不再写盘；对话框弹出后编辑器仍可编辑（步骤 02 §5.4 的决策） |
| 「另存副本」时新章标题冲突 | 服务端按 `slug` 去重（`domain/paths.py` 已有逻辑），失败则对话框内报错并保留三选一界面，不关闭 |
| flush 期间用户又改了内容 | `flush()` 内部是循环 + 串行闸门，会等到"当前批 + 补偿批"都落盘才返回 true（该实现有注释详述） |

## 10. 验收标准

| # | 项 | 判定 |
|---|---|---|
| 1 | **A5 外部改动被拦下** | 应用里打开某章 → 用 VS Code 改 `chapter.md` → 在应用里打字 → 出现"文件被外部修改"，点「重载」后编辑器显示磁盘版本、自己的改动被丢弃且**磁盘文件未被覆盖** |
| 2 | A5 的覆盖路径 | 同样场景下选「保留我的并覆盖」→ 磁盘变成我的内容，且 `.inkstone/backups/` 下出现 `{chapterId}-{时间戳}.md`，内容 = 被覆盖的那一版 |
| 3 | A5 的副本路径 | 选「另存副本」→ 侧栏出现新章（此时侧栏可能还没做，用文件管理器核对目录），当前章显示磁盘版本 |
| 4 | **A4 正常关闭零丢失** | 连续打字不停手，直接点窗口关闭 → 重开应用，**最后敲的字在** |
| 5 | A4 强杀 ≤ 3 秒 | 打字过程中用任务管理器结束进程 → 重开，丢失不超过 3 秒的输入（`maxWait` 的承诺） |
| 6 | A4 强调边界 | 拔掉/关停 sidecar 进程后打字 → 出现"保存失败"提示且**编辑器内容不丢**；主进程自动重启 sidecar 后点「重试」→ 落盘成功 |
| 7 | 失败时应用仍可关闭 | sidecar 处于失败态时点关闭 → 3 秒内弹出「有内容尚未保存」确认框，点「仍要退出」即关闭（**注意不是超时路径**，见 §12.5）；无未保存内容时直接关闭，不卡住 |

## 12. 实现注记与偏差（v0.2）

### 12.1 文件清单变化：新增 `conflict-actions.ts`

```
features/editor/conflict-actions.ts   # §6.2 三条路径的纯编排
```

**为什么必须多这一个文件**：§6.2 里有**两处"写错就静默毁掉用户内容"的点**

所以把编排抽成不依赖 React 的纯函数，`useAutosave` 只负责把结果接回状态机 ——
这也让钩子自己几乎没有"需要小心写"的分支。

`preload/index.ts`、`renderer/src/env.d.ts`。

### 12.2 §4.1 的依赖数组：`client` 走 ref，**不进依赖**

原文写的是"依赖数组只放 `chapter.id` 与 `client`"。**`client` 不能进依赖**：

sidecar 崩溃重启后端口会变，步骤 01 的 `useApiClient` 会因此重建 `ApiClient`。
把 `client` 放进依赖，那次重建就会把 `Autosave` 实例连同 `mustSave` 一起丢掉 ——
用户在这几秒里敲的字**静默消失**，而界面还会显示"已保存"。
改成 ref 之后实例活过重启，那批改动留在 `mustSave` 里，服务回来自动重试或点「重试」即可落盘。

副作用（正面）：`save` 里必须自己判 `client === null`，此时抛 `ApiError(NETWORK_ERROR_CODE)`，
让它走"可重试"分支而不是普通错误 —— 重启期间失败的这批内容恰恰最该能重试。

实际依赖数组：`[chapter.id, workId]`。`workId` 一起进，是因为换作品时章节 id 有可能重名。

### 12.3 §4.1 的 `onWarnings` 入参已删除

原文签名里有 `onWarnings: (w: AdapterWarning[]) => void`，实现里**没有这一项**：
保存时的序列化与 `EditorPane.onChange` 里的序列化是同一次 `toJSON()` 的同一份结果
（`Autosave.onChange` 本来就是由那次编辑触发的）。再加一条通道只会造出**第二个真源**，
与本仓"正文只能有一个来源"的约定冲突。导出侧告警继续由 `EditorPane` 统一发布。

### 12.4 返回类型的两处补充

| 原文 | 实现 | 理由 |
|---|---|---|
| `error: string \| null` | `error: string \| null` **+ `canRetry: boolean`** | 401 不给重试是 §8 的规则。判断不能散在组件里，所以由 `describeSaveError` 固化 |
| 无 | **+ `savedAt: string \| null`** | `Autosave` 只在 `onStateChange` 给状态、不给时间，而指示器要显示相对时间。在 `save` 成功处记一份 |

另外 `handle: Autosave` 实际是 `handle: Autosave | null`：`WorkShell` 的钩子必须在早返之前调用，
而"打开中/打开失败"两种状态下没有章节，也就没有实例。

### 12.5 §7.2 的关闭分支：超时直接 destroy，`ok:false` 一定弹确认框

实现与原文一致（超时走第三支直接关闭），但要补一句**验收第 7 项的实际路径**：

sidecar 处于失败态时点关闭，渲染进程会**立刻**用 `{ ok: false }` 回话
（`flush()` 在 `error` 态直接返回 `false`，不等待网络超时），于是走的是**确认框**分支，
不是超时分支。这是有意的 —— 静默关掉等于替用户决定了"丢掉这几个字"。
超时分支只覆盖"渲染进程整个卡死"这一种情况：此时我们**无从知道**有没有未落盘内容
（问不出来），而"绝不允许关不掉"是硬规则（§7.3 第 1 条），所以直接关闭是唯一的安全出口。
超时会在 stderr 留一行记录，便于事后追查。

因此原文 §10 第 7 项的判定应改读为：**sidecar 失败态点关闭 → 3 秒内弹出确认框且应用可关闭**。

### 12.6 冲突对话框加了「稍后处理」出口

§6.1 要求冲突时自动弹出对话框，§8 又要求"对话框弹出后编辑器仍可编辑" ——
全屏遮罩不放行就等于把编辑锁死，两条要求直接冲突。折中：

- 冲突出现 → **自动弹出**（否则一个窄条上的状态变化太容易被漏掉）
- 对话框右上角「稍后处理」→ 关掉继续写。冲突不解决并不丢字（内容还在编辑器里，只是不再自动写盘）
- 状态指示停在「文件被外部修改」且可点击 → 随时回到对话框

### 12.7 编辑区的滚动与内边距改由 `.editor-host` 接管

错误条 / 备份提示插在编辑面板之上后，`.editor-pane` 的 `height: 100%` 会把它顶出可视范围，
且内外两层各出一条滚动条（`.work-content` 的 `overflow: auto` + `.inkstone-editor` 的）。
处置：`<main class="work-content editor-host">` + `.editor-stack` 内部用 `flex: 1` 分配剩余空间。
选择器写成两个类（0,2,0）是为了稳压住 `global.css` 的 `.work-content`（0,1,0）——
靠加载顺序决定胜负太脆。

视觉上的后果：编辑区少了 `work-content` 那 14/16px 内边距。正文本身有
`max-width: var(--editor-measure)` 居中，观感反而更整齐。

### 12.8 备份提示的位置

§5 只说"显示一次性提示"，没说放哪。实现放在编辑区顶部（错误条同侧），
不放页头：页头是"作品名 + 状态 + 章节 + 返回"四件套，塞一个带绝对路径的长条会把它挤变形。

### 12.9 其它

- 关窗等待上限 `FLUSH_TIMEOUT_MS = 3000`，与 `Autosave.maxWait` 同值：一次 flush 最多两轮写入，是宽松上界。
- 超时/卡死会往 **stderr** 记一行（stdout 是 sidecar 的握手通道，绝不占用）。
- `docs/02` §5.3 的 IPC 白名单已同步补两行，并注明为何用 `send`/`on` 而非 `invoke`。
- 状态指示的错误文案刻意短（「保存失败」），完整安抚句由 `SaveErrorBar` 承担 ——
  指示器是个窄条，塞长句会被截断。
