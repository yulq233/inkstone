## 2. 前置验证结论（9 个坑，全部实测确认）

写代码前逐条核过依赖包的真实类型定义与实现。**这些不是理论风险，是照着文档写就会出错的地方。**

| # | 坑 | 证据 | 踩了会怎样 |
|---|---|---|---|
| 1 | **`setContent` 第二个参数是 options 对象，不是布尔值** | `@tiptap/core` d.ts:3822 + 实现 `(content, { emitUpdate = true } = {})` | `03` 文档 §6.5 第 7 步写的 `setContent(doc, false)` 是 **v2 写法**。v3 里传 `false` 会被解构成"全 undefined"，`emitUpdate` 取默认值 **true** —— 于是切章时触发 `onChange` → `Autosave` 拿**旧 baseHash** 立刻发一次 PUT → **弹出莫名其妙的冲突对话框** |
| 2 | ~~`setContent` 接受 `Content \| Fragment \| Node`~~ → **该结论已作废，见下方修订** | `@tiptap/core` 的 `isProseMirrorContent()` 只看"有没有 `nodesBetween` 方法"，任何 PMNode 都会被原样放行 | 见坑 #10 |
| 3 | **JSDoc 与实现不一致** | 同处注释仍写 `@param emitUpdate Whether to emit...` | 照 JSDoc 抄就错。以实现签名为准 |
| 4 | `setEditable(editable, emitUpdate?)` 才是**独立布尔参数** | core d.ts:4349 | 两个 API 参数形状不对称，写的时候容易互相串味 |
| 5 | **`toMd(doc: PMNode)` 不接受 JSON** | `md-adapter/src/to-md.ts:168` | 导出必须传 `editor.state.doc`。传 `editor.getJSON()` 是类型错误（运行时则静默产出空内容） |
| 6 | md-adapter **不依赖 `instanceof`**；`prosemirror-model` 全仓**只有一份 1.25.11**（hoisted 布局，非 pnpm 链接布局），`@tiptap/pm@3.31.3` 同版本 | `grep instanceof` 无命中 + 依赖树核对 | → 跨包把 TipTap 的 `state.doc` 喂给 `toMd` **是安全的**，不存在"两个 prosemirror-model 实例导致判断失效"的问题 |
| 7 | `useEditor` 有两个重载：不传 `immediatelyRender` 返回 **`Editor`**；传 `false` 返回 **`Editor \| null`** | `@tiptap/react` d.ts:7-18 | 桌面环境**不设** `immediatelyRender` —— 它只是 SSR 的补丁。设了反而要多写判空，且容易照抄 Next.js 的写法引入无意义分支 |
| 8 | **`body { user-select: none }`** | `renderer/src/styles/global.css:62` | 不覆盖成 `user-select: text`，编辑器里**一个字都选不中**、也无法拖选 —— 而 ProseMirror 的选区是核心机制 |
| 9 | TipTap **不带任何样式** | 包结构（无 css 入口） | 不写 `.ProseMirror` 的基础排版，段落会挤成一坨、连续空格被折叠、空段落没有高度 |

### 实现时新增的三条（v0.2，均已实测）

| # | 坑 | 证据 | 结论 |
|---|---|---|---|
| 10 | **`setContent` 不能直传适配层的 PMNode**（推翻坑 #2） | `prosemirror-model/dist/index.js` 的 `ContentMatch.matchType()` 是 `if (this.next[i].type == type)` —— **身份**比较；`validContent()` 依赖它。`test/editor-schema-bridge.test.ts` 断言 `editorSchema.nodes.doc.createChecked(null, fromMd(…).doc.content)` **抛错**且该用例通过 | 一律 `setContent(doc.toJSON(), { emitUpdate: false })`，让编辑器用自己的 schema 重建节点。直传的后果不是抛错，而是节点带着**外来 schema 的 type** 留在文档里，之后每次编辑都可能踩到身份比较 |
| 11 | **`create` 事件是异步发出的** | `@tiptap/core` 的 `mount()` 里 `window.setTimeout(() => { … this.emit("create", …) }, 0)` | 好处：`onCreate` 不在渲染期触发，`onReady` 里 `setState` 不会踩"渲染期更新另一个组件"。代价：**章节内容比编辑器先到是常态**，所以载入 effect 的依赖里必须放 `editorReady`，否则那一次 `setMarkdown` 会丢 |
| 12 | **`toMd` 不在块之间插空行** | 实测 `toMd` 输出 `# H1\n\n正文\n> 引用\n\n---\n` | 这是对的（方言里"一行即一段"，空行只是分隔符），但**别手写整串字面量当期望值** —— 改为断言"再解析再序列化不漂移"这个真正的不变量 |

### §5.3 开放问题已闭环（v0.2）

原文档留的疑问"`fromMd('')` 是否已包含一个空段落，为空则要兜底"——**已经有兜底了**，
不需要额外处理：`from-md.ts` 末尾 `blocks.length > 0 ? blocks : [emptyParagraph()]`。
空章节打开后光标可见、能直接打字。

> 验证方法记录：`setContent` / `setEditable` / `useEditor` / `toMd` 的签名直接读 `node_modules` 下的 `.d.ts` 与实现；`prosemirror-model` 副本数用 `Get-ChildItem` 扫 `node_modules` 布局 + 读 hoisted 包的 `package.json`；`instanceof` 用全仓 grep。v0.2 追加：`matchType` / `validContent` / `mount` / `EditorInstanceManager.createEditor` 逐段读实现，并把结论固化成 `test/editor-schema-bridge.test.ts` 的断言。

## 4. 接口设计

### 4.1 为什么用 imperative handle 而不是透出 `Editor`

如果 `EditorPane` 把 TipTap 的 `Editor` 对象一层层传出去，步骤 03/04 的组件就得 `import type { Editor } from '@tiptap/core'` —— 编辑器库的类型会渗到整个渲染进程，将来换内核要改一圈。

所以只暴露三个动词，其中"读写正文"这两个恰好就是适配层的两个方向：

```ts
// features/editor/TipTapEditor.tsx
export interface EditorHandle {
  /** PM → Markdown。内部走 toMd(editor.state.doc)（坑 #5） */
  getMarkdown(): ToMdResult;
  /** Markdown → PM → 文档。返回 warnings 供告警条展示 */
  setMarkdown(markdown: string): { warnings: AdapterWarning[] };
  /** 光标移到文首（切章后调用） */
  focusStart(): void;
}

export interface TipTapEditorProps {
  placeholder?: string;
  editable?: boolean;
  /** 内容变化。**刻意不带参数** —— 正文只有一个来源（getMarkdown），两处来源必然漂移 */
  onChange: () => void;
  /** 编辑器就绪。用于把 handle 交给上层 */
  onReady: (handle: EditorHandle) => void;
}
```

`onChange` 不带参是刻意的：TipTap 的 `onUpdate` 能拿到 `transaction`，顺手从里面取内容看起来很方便 —— 但那会造出第二条正文来源（`transaction` 里的 doc vs `editor.state.doc`），两者在批量更新时可能不一致。统一走 `getMarkdown()`。

### 4.2 组件内部

```tsx
const editor = useEditor({
  extensions: createEditorExtensions(placeholder),   // 已含白名单断言
  editable,
  onUpdate: () => onChangeRef.current(),             // 用 ref 包一层，避免每次渲染重建编辑器
  onCreate: ({ editor }) => onReadyRef.current(makeHandle(editor)),
});
return <EditorContent editor={editor} />;
```

`extensions` 必须**每次渲染都传入同一个引用**（在模块顶层或在 `useMemo` 里构建一次）。TipTap 会在 deps 变化时重建实例 —— 传入内联数组字面量会让编辑器在每次父组件渲染时重建，症状是"打字时焦点乱跳"。

`makeHandle` 的实现：

```ts
function makeHandle(editor: Editor): EditorHandle {
  return {
    getMarkdown: () => toMd(editor.state.doc),
    setMarkdown: (markdown) => {
      const { doc, warnings } = fromMd(markdown);
      // 坑 #1：必须是 { emitUpdate: false }，不能写 setContent(doc, false)
      // 坑 #10：必须 toJSON() 中转，不能直传 doc
      editor.commands.setContent(doc.toJSON(), { emitUpdate: false });
      return { warnings };
    },
    focusStart: () => editor.commands.focus('start', { scrollIntoView: false }),
  };
}
```

`setMarkdown` 外层包了 `try/catch`：`fromMd` 抛出时**兜底渲染纯文本**（整章塞进一个段落，
内容一个字不少），并把这件事报进告警条 —— 绝不出现"打开是白板"（§8）。

## 5. 关键流程

### 5.1 载入一章

```
上层调 handle.setMarkdown(chapter.markdown)
  └─ fromMd(markdown) ──► { doc: PMNode, warnings }
       ├─ setContent(doc, { emitUpdate: false })   ← 不触发 onChange（坑 #1）
       └─ return { warnings } ──► EditorPane.setState(warnings)
                                    └─ 非空 → 显示 AdapterWarningsBar
```

**`emitUpdate: false` 是整条链路的关键**：置 false 后 TipTap 会在事务上打 `preventUpdate` 标记，不会触发 `onUpdate`。这样"载入内容"与"用户输入"在 `Autosave` 眼里就是两件事 —— 前者不该被记为待保存。

### 5.2 导出（供 Autosave 的 `getMarkdown` 调用）

```
Autosave.opts.getMarkdown() ──► handle.getMarkdown()
                                  └─ toMd(editor.state.doc) ──► { markdown, warnings }
```

导出时的 `warnings` 也要展示。产生原因是用户在编辑器里做了 `toMd` 无法表达的操作（理论上不可能，因为扩展集受白名单约束，但**降级告警宁可多报不可漏报**：它一旦漏报，就等于静默改了用户的稿子）。

### 5.3 空文档

`md-adapter` 已导出 `emptyParagraph()`。`fromMd('')` 的结果需要确认是否已包含一个空段落（`fromMd` 的既有测试覆盖了空串），若返回的 `doc` 内容为空，`setContent` 会让编辑器处于"没有可打字的地方"的状态。**实现时先跑一次 `fromMd('')` 看结果**，为空则用 `inkstoneSchema.node('doc', null, [emptyParagraph()])` 兜底。

### 5.4 只读态

| 场景 | editable |
|---|---|
| 正常 | `true` |
| 保存出错（`ERROR`） | `true` —— **不改只读**。本地优先的产品，服务写不进去不该阻止用户继续写；内容仍在编辑器里，重试即可 |
| 冲突未解决（`CONFLICT`） | `true` —— 同上。只暂停自动保存（那已在 `Autosave` 里做了），不动编辑器 |
| 章节尚未载入 | 面板显示加载态，编辑器不挂载（避免 `setMarkdown` 打到一个空实例上） |

**为什么冲突时也不锁编辑器**：用户的字已经在屏幕上了，锁掉它只会让人以为内容丢了。要解决的是"往哪写"，不是"能不能写"。

## 7. 降级告警条契约（`03` 文档 §5.8）

| 项 | 决定 |
|---|---|
| 位置 | 编辑器上方，整条横幅（不用 toast） |
| 文案 | `检测到 N 处不支持的格式，已按纯文本保留` + 「查看」展开明细 |
| 明细 | 每条：`message`（来自 `AdapterWarning`）+ 原文片段（用 `from`/`to` 从 markdown 切片） |
| 可否关闭 | 可折叠，但**每次重新载入章节都会再出现** —— 降级是持久状态，不是一次性事件 |
| 何时清空 | 只在下次 `setMarkdown` 时重算。不做"编辑后自动消失"（那会骗用户） |

**为什么不用 toast**：toast 三秒后消失，而这条信息的性质是"你稿子里有一段东西没能完整显示"。消失等于遗忘。

`warning-text.ts` 提供纯函数：

```ts
export function summarizeWarnings(warnings: AdapterWarning[]): string;
export function describeWarning(w: AdapterWarning, markdown: string): { title: string; excerpt: string };
```

## 8. 异常与边界

| 场景 | 行为 |
|---|---|
| `fromMd` 抛错 | **兜底渲染纯文本**：不空白、不报错弹窗。做法是把 markdown 包成单个段落节点再 `setContent`，同时告警条显示"该章内容未能完整解析"。绝不出现"打开是白板" |
| `warnings` 极多（几百条） | 明细只渲染前 50 条 + "还有 N 条"，避免长列表卡住 |
| 连续 `setMarkdown`（快速切章） | 后一次调用直接覆盖，不做队列。切章时序（步骤 03）保证不会并发 |
| 编辑器实例未就绪 | `handle` 未产出前，`EditorPane` 显示 loading，上层拿不到 handle 就不该发 `setMarkdown` |
| 超大章节（10 万字） | 不做虚拟滚动（M0），但要在步骤 07 的性能基线里记录首次渲染耗时 |
| IME 输入中文 | 不拦截 `keydown` 做快捷键，避免打断输入法组合态（`Mod-B` 交给 TipTap 的 input rules / 原生快捷键） |

|---|---|
| `summarizeWarnings` 复数与单数文案 | `1 处` / `3 处`；空数组返回**空串**（调用方据此不渲染） |
| `dedupeWarnings` 去重与顺序 | 载入侧与导出侧的重复告警只留一份 |
| `describeWarning` 的片段切片边界 | 两端、跨行、`from === to`（导出侧）、越界夹紧、**按码点**截断不切坏代理对 |
| **`editor-schema-bridge.test.ts`（v0.2 新增）** | 把坑 #10 固化成断言：直传 PMNode 被内容校验拒绝 → 所以必须 `toJSON()`；并验证走 JSON 后两个方向都接通、往返不漂移 |

`EditorHandle` 两个方向的贯通由上面的桥接测试覆盖，不重复 `md-adapter` 已有 140 项往返测试。

## 10. 验收标准

| # | 项 | 判定 |
|---|---|---|
| 1 | 打开的章节内容与 `chapter.md` 一致 | 用外部编辑器造一段含 H1/H2/H3、加粗、斜体、引用、分隔线的正文，应用内显示一致 |

## 11. 风险

| 风险 | 对策 |
|---|---|
| `useEditor` 的 deps 处理不当导致实例重建 | `extensions` 只构建一次；`onUpdate` / `onReady` 用 ref 包住；**在 deps 数组里不传任何值**（默认只创建一次） |
| `toMd` 遇到 TipTap schema 特有的节点属性 | 已确认 `toMd` 只读 `type.name` 与 `attrs.level`，不依赖 instanceof（坑 #6）；新增扩展时必须同步改白名单与序列化 —— 那条断言会拦 |
| 中文排版观感 | 样式只定基础版式，留白与字号交给步骤 06 的主题；本步骤以"能读能写"为验收线 |
| 大章节首次渲染慢 | 记入步骤 07 的性能基线，不在本步骤优化 |

## 12. 实现说明（v0.2 补充，代码已落地）

### 12.1 切章会重建编辑器实例，这是**刻意**的

`useCurrentChapter` 在切换章节时把 `content` 置 null → `EditorPane` 显示加载态 → 编辑器卸载；
新正文到达后重新挂载。代价是每次切章重建一次 TipTap 实例，收益有两条：

- 撤销历史**不会跨章**。跨章的 undo 一旦生效，就是"我在第三章按 Ctrl+Z，第二章被改了"。
- 不需要处理"旧实例灌新内容"的中间态。

步骤 04 若改成"保留实例 + `setMarkdown` 覆盖"，要显式处理撤销历史的隔离 —— 别顺手改掉这一条。

### 12.2 字数与导出告警现在合并到最多每 200ms 一次（`docs/13` M22）

**口径**部分不变，且必须继续遵守：一次 `getMarkdown()` 同时喂给"字数条"与"导出侧告警"，
刻意**不**改用 `doc.textContent` 算字数 —— 标题的 `# `、引用的 `> `、转义反斜杠都不在正文里，
两个口径必然对不上，而 sidecar 写进 `meta.json` 的是 markdown 口径 ——
那会变成"界面显示 N 字、重启后变 N+1"。

**频率**部分改了。v0.2 原本写"暂不节流，等步骤 07 的性能基线"。第 5 批后续组
的代码审查（`docs/13` M22）提前把它变成事实：一次输入跑两趟 O(全文)
（全量 `toMd` + `countWords`），几万字的章节连打十个字就是二十趟，
掉帧掉在**打字**这条最敏感的路径上。而这两个值只是给人看的近似值，晚 200ms 无感。

落点是 `lib/coalescer.ts`：

- **合并语义是"已排队就只合并、不重置计时器"**，不是经典 debounce。debounce 下
  一直打字就永远不触发，字数条会在整段输入期间冻住；合并语义下最多等 200ms，
  停手后一定算到（尾部不减）。
- `handleChange` 里 `onChange?.()`（→ `Autosave`）**仍然每次都调** ——
  保存节流是 Autosave 自己的事，这里漏一次就是漏一个待保存标记。
- 导出侧告警先过 `warning-text.ts::sameWarnings`，内容没变就保持旧引用：
  它绝大多数时候是空数组，换个新引用会让下游 `useMemo`（去重）与告警条白重渲染一次。

**两个实现约束**（都实测过）：

1. 实例必须**在 effect 里**创建，不能用 `useState` 惰性初始化 —— 创建时要捕获
   读 `handleRef` 的 `recomputeMetrics`，而渲染期引用这样的函数会被
   `react-hooks/refs` 判成"渲染期访问 ref"（实测报 error，不是 warning）。
2. 重算函数拆成独立的 `useCallback`，deps 为空 → 引用稳定 → 那个 effect 只跑一次。

### 12.3 告警的 `from`/`to` 是**原文**下标（`docs/13` M26）

`AdapterWarningsBar` / `warning-text.ts::describeWarning` 拿 `from`/`to` 去切
**调用方交给 `fromMd` 的那份 markdown**。而这两个数此前是"归一化**之后**的下标" ——
归一化会增删字符（BOM -1、`\r\n`→`\n` 每行 -1、剪行尾空白、给标题/分隔线补空行），
于是 CRLF 章节里告警摘录会错位、串到上一行。

修法：`normalize.ts` 改成逐行并带回**原文起点** `origin`（新增 `normalizeToLines` /
`NormalizedLine`），`from-md.ts` 的行号与告警偏移一律用 `origin`；
归一化**补出来**的空行记 `origin: -1`（它不是原文里的任何一行）。

两个坑：

- `split(/\r\n|\r|\n/)` **不能**用"上一行起点 + 行长 + 1"递推下一行起点 ——
  `\r\n` 是**两个**字符，每行都会差一位。必须自己扫 `/\r\n|\r|\n/g`
  并按 `match[0].length` 推进。
- 告警的 `to` 是 `origin + 归一化后行长`，**两端不在同一个坐标系**：
  起点是原文坐标，长度是归一化后的长度。别按"原文里那一行多长"去理解它
  （`types.ts` 的 doccomment 已写明；`pitfalls.test.ts` 有一条专门钉这个区间的切片结果）。

### 12.4 行首消歧要看**归一化之后**的样子（`docs/13` M28）

`to-md.ts::escapeLineStart` 决定"这段文字落盘时要不要在前面加反斜杠"，
原本在归一化**之前**判断行首。而归一化的第 3 步会剪掉行尾空白，于是：

```
用户敲的段落内容：`---   `（三个短横 + 三个空格）
归一化前判断：`/^-{3,}$/` 匹配不上（多出的空格让它"不像分隔线"）→ 不加反斜杠
落盘：被剪成 `---`
下次解析：变成一个分隔线 —— 内容没了，而且没有任何告警
```

判据因此改成先算 `probe = line.replace(/[ \t]+$/, '')`，再用 `probe` 判三种块级前缀
（`^-{3,}$` / `^#{1,6}[ \t]` / `^>`），反斜杠加在**原样**那一行上。
"归一化之后会长成什么样"才是有效判据 —— 因为落盘与解析都发生在归一化之后。
