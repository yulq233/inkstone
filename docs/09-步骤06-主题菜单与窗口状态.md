## 0. 为什么这三件"小项"合成一步

它们共享同一套基础设施：**主进程侧的持久化存储（`main/store/`）+ 主进程与渲染进程之间的设置通道**。分开做会把这个基础设施重复实现三遍。

同时它们都是"用户每天都会碰到、但一直没做"的东西：主题是打开应用第一眼看到的，菜单是找不到功能时的兜底入口，窗口状态是"每次打开都得重新拉窗口大小"的烦躁来源。M0 作为可交付的版本，这三件不该缺。

## 1. 范围

### 1.1 做

- **主题**：跟随系统 / 浅色 / 深色 + 编辑器字号 + 行距，重启后保留
- **主进程菜单**：文件 / 编辑 / 视图 / 帮助
- **窗口状态持久化**：位置、尺寸、最大化

### 1.2 不做

| 不做 | 理由 |
|---|---|
| 完整的设置页（外观 / 快捷键 / 目录 / 模型…） | `02` 文档 §1.2 已把"设置页"划到 M4。本步骤只做**外观相关的最小设置**，落在一个轻量面板里 |
| 自定义快捷键 | M1 |
| 主题配色方案的市场 / 导入 | 不做 |
| macOS 的应用菜单特殊处理（`appMenu` role） | M0 只出 Windows（`02` §1.2） |
| 多窗口 / 窗口尺寸记忆 per-work | 单窗口应用，一套尺寸就够 |

### 2.1 发现一：菜单栏当前是被**刻意隐藏**的

```ts
// apps/desktop/src/main/window.ts:17
autoHideMenuBar: true,
```

所以"没有菜单"不是遗漏，是当前的选择。加菜单时要一并决定它的可见性（§4.1）。

### 2.2 发现二：窗口背景色硬编码，且与 CSS 变量**不是同一个值**

```ts
// window.ts:16
backgroundColor: '#f7f6f3',
```
```css
/* global.css:2 */
--bg: #faf9f7;
```

两个后果：

1. **深色主题下启动会白闪** —— 窗口先用 `#f7f6f3`（浅色）铺底，渲染进程加载后才换成深色变量。用户看到一次明显的白光。
2. **浅色下也会有一次轻微跳色** —— `#f7f6f3` 与 `#faf9f7` 不同，首帧与稳定态之间有肉眼可辨的色差。

修法见 §3.5。这是本步骤顺带修掉的一个真问题。

## 3. 主题设计

### 3.1 三态而不是两态

```ts
export type ThemeMode = 'system' | 'light' | 'dark';
```

**`system` 必须是默认值**，且它和"用户手动选了浅色"要能区分开 —— 否则用户选了一次浅色，之后系统切深色就不跟随了，而他以为自己选的是"跟随"。这个区别只能靠三态表达。

### 3.2 CSS 变量层的改造

现状是 `@media (prefers-color-scheme: dark)` 直接覆盖变量。改成**属性选择器优先、媒体查询兜底**：

```css
:root { /* 浅色变量（现值不动） */ }

/* 显式深色 */
:root[data-theme='dark'] { /* 深色变量 */ }

/* 跟随系统：仅当没有显式指定时生效 */
@media (prefers-color-scheme: dark) {
  :root:not([data-theme='light']):not([data-theme='dark']) { /* 深色变量 */ }
}
```

深色变量在两个地方重复。用 CSS 自定义属性没法避免 —— 但可以避免**手抄**：把深色块抽成一个共享的 `@layer` 或用 PostCSS 的 mixin。M0 选择**手抄一次并加注释**，理由是引入 PostCSS 插件链的复杂度大于这份重复的维护成本（两处相邻，改一处时必然看到另一处）。

渲染进程在挂载时把 `ThemeMode` 写到 `<html data-theme>`：

```ts
// system 时**不写** data-theme，交给媒体查询
document.documentElement.dataset.theme = mode === 'system' ? '' : mode;
```

### 3.3 字号与行距

走 CSS 变量，作用域限在编辑器（步骤 02 的 `editor.css` 已预留）：

| 变量 | 默认 | 范围 | 步进 |
|---|---|---|---|
| `--editor-font-size` | `16px` | 14 ~ 22 | 1px |
| `--editor-line-height` | `1.8` | 1.5 ~ 2.4 | 0.1 |

**只影响编辑器，不影响界面其他部分**。界面字号保持 14px 不动 —— 用户调的是"读稿子的舒适度"，不是"整个软件的缩放"。

写作应用的字号默认给 16px（当前全局 14px 对长时间阅读偏小）；行距默认 1.8 已是长文阅读的舒适区。

### 3.4 存储：`main/store/settings.json`

```jsonc
// %APPDATA%/砚台/settings.json
{
  "schemaVersion": 1,
  "theme": { "mode": "system", "fontSize": 16, "lineHeight": 1.8 },
  "window": { "x": 120, "y": 80, "width": 1180, "height": 780, "maximized": false }
}
```

**为什么不放 `localStorage`**：

| 方案 | 问题 |
|---|---|
| `localStorage` | 清缓存/重装即丢；且主进程读不到（窗口状态必须主进程读，才能在建窗口时就用上） |
| sidecar | 主题是**界面偏好**，不是作品数据。放 sidecar 意味着"sidecar 挂了主题就没了"，而主题恰好在 sidecar 启动失败时最需要（错误页也要正确配色） |
| **主进程 `userData` 下的 JSON** | 主进程与渲染进程都能读；与 `logs/` 同处一个目录，排查问题只去一个地方；sidecar 挂了照样可用 |

沿用 sidecar 侧 `work.json` 的三条原则（`03` 文档 §4.2）：`schemaVersion` 只认 1、未知字段保留、缺失字段补默认并写回。同一套自愈逻辑，两处行为一致。

### 3.5 修掉启动闪白

窗口创建前读一次设置：

```ts
// main/window.ts
const settings = loadSettings();
const dark = settings.theme.mode === 'dark'
  || (settings.theme.mode === 'system' && nativeTheme.shouldUseDarkColors);

const win = new BrowserWindow({
  ...,
  backgroundColor: dark ? DARK_BG : LIGHT_BG,   // 与 global.css 的 --bg **同一个值**
});
```

`DARK_BG` / `LIGHT_BG` 从 `global.css` 的 `--bg` 取值（`#faf9f7` / `#1c1b19`），两侧硬编码同一份常量并加注释互相指认。**顺手把 `#f7f6f3` 这个不一致的值改掉。**

`nativeTheme.shouldUseDarkColors` 只在 `app.whenReady()` 之后可靠 —— 窗口就是在 ready 之后创建的，顺序天然满足。

### 3.6 设置通道

新增两个 IPC：

| 通道 | 方向 | 载荷 |
|---|---|---|
| `settings:get` | 渲染 → 主 | 返回 `Settings`（启动时读一次，缓存在渲染进程） |
| `settings:set` | 渲染 → 主 | `Partial<Settings>`，主进程合并后落盘并广播 `settings:changed` |

**主题切换不走"读一次等回复"**：渲染进程内存里有当前设置，切换时**先改 CSS 变量（立即生效）**，再 fire-and-forget 发 `settings:set`。持久化失败不该让主题切换卡顿。

`settings:changed` 广播给渲染进程，是为了"多窗口 / 刷新后同步"这类场景（M0 只有一个窗口，但通道留着不吃亏）。

## 4. 菜单设计

### 4.1 菜单栏可见性

现状 `autoHideMenuBar: true`。**建议改为 `false`（常显）**，理由：

- 这是 Windows 桌面应用，菜单栏常显符合用户预期
- M0 的功能入口本来就少（新建/打开作品、切换主题），菜单是主要的**可发现性**来源；藏在 Alt 后面等于没有
- 快捷键（`Ctrl+N` / `Ctrl+O`）仍然可用，菜单只是把它们的可见性补上

若嫌占地，可后续加"隐藏菜单栏"的开关 —— M0 不做这个开关。

### 4.2 菜单结构

```
文件  新建作品        Ctrl+N
      打开作品…       Ctrl+O
      ─────────────
      关闭作品
      ─────────────
      退出            Alt+F4（role: quit）

编辑  撤销            role: undo        ← 见 §4.3，可能要改
      重做            role: redo
      ─────────────
      剪切/复制/粘贴    role: cut/copy/paste
      全选            role: selectAll

视图  主题：跟随系统 / 浅色 / 深色     （单选，radio 类型）
      ─────────────
      放大字号        Ctrl+=      （行为转发给渲染进程）
      缩小字号        Ctrl+-
      重置字号        Ctrl+0
      ─────────────
      重新加载        role: reload（仅开发态可见）
      开发者工具      role: toggleDevTools（仅开发态可见）
      ─────────────
      全屏            role: togglefullscreen

帮助  关于砚台
      打开日志目录    （排查问题时最常用的一项）
```

### 4.3 关键风险：`role: 'undo'` 与 ProseMirror 可能打架（**必须实测**）

Electron 的 `role: 'undo'` 最终调用 `webContents.undo()`，走的是 Chromium 的原生编辑撤销栈。而 **ProseMirror 的撤销栈由 `prosemirror-history` 自己维护**，两者不是一套东西。

风险在于：原生撤销可能绕开 ProseMirror 的插件直接改 DOM，被 ProseMirror 的 DOM observer 捕获成"外部变更" —— 轻则撤销一次跳回很久以前，重则文档状态错乱（而文档状态错乱意味着**存盘存进去一堆乱结构**）。

落地策略：

```
第一步：按 role: 'undo' / 'redo' 实现，然后实测
  用例：连打 10 段 → Ctrl+Z 撤 3 次 → 再打一段 → 保存 → 用外部编辑器看 md
  ├─ 行为正常（撤销粒度与编辑器内 Ctrl+Z 一致）→ 保留 role
  └─ 异常（跳步、改坏结构、撤销后字数对不上）→ 改成下面的转发写法

第二步（保险方案）：菜单项 click 里发 IPC 给渲染进程，由编辑器自己执行
  main:   { label: '撤销', accelerator: 'CmdOrCtrl+Z', click: (_, win) => win?.webContents.send('editor:command', 'undo') }
  渲染:   收到后调 editorHandle.undo()  →  内部是 editor.commands.undo()
```

**注意方向**：菜单的"撤销"与键盘 `Ctrl+Z` 是两条路径。键盘那条由 ProseMirror 的 keymap 直接处理，**本来就是对的**（所以即使菜单项有问题，日常撤销也不会坏）。菜单这条路要额外验证。

### 4.4 菜单项的状态（禁用/勾选）

菜单重建成本高，M0 的做法：

- **不做"当前没有作品时禁用文件菜单项"** —— 需要主进程知道渲染进程状态，多一条同步通道，收益很小（点了没反应 vs 点了被禁用，对用户差别不大）
- **主题的单选项需要勾选态** —— 主进程持有设置，`Menu.getApplicationMenu()` 可动态改 `checked`。切换时重建菜单（菜单小，重建成本可忽略）
- 所有实际动作（新建作品、切主题、调字号）都**由主进程发 IPC 给渲染进程执行**，主进程不直接操作业务状态 —— 保持"业务状态在渲染进程"这条边界（`02` 文档 §2.2）

## 5. 窗口状态持久化

### 5.1 保存什么

`x` / `y` / `width` / `height` / `maximized`。

### 5.2 恢复时必须做越界检查（**这是最容易漏的一步**）

用户把窗口放在外接显示器上 → 拔掉显示器 → 下次启动窗口跑到屏幕外，**完全看不见，只能删配置文件救回来**。

```ts
function ensureOnScreen(bounds: Rectangle): Rectangle {
  const displays = screen.getAllDisplays();     // 必须在 app.whenReady() 之后调用
  const visible = displays.some((d) => intersects(d.workArea, bounds));
  return visible ? bounds : { ...bounds, x: undefined, y: undefined };  // 交给系统居中
}
```

判定用**交集**而非"包含"：窗口只有一部分在屏幕内也算可见（用户能拖回来）。

`screen` 模块在 `app.ready` 之前调用会抛错（Windows 上表现为返回空数组）—— 窗口创建本来就在 ready 之后，顺序满足；但要在代码里加注释标明这个约束，防止有人把它挪到 ready 前。

### 5.3 保存时机

| 时机 | 值 |
|---|---|
| `resize` / `move` | **debounce 500ms** —— 拖拽窗口会每秒触发几十次，直接写盘是浪费 |
| `maximize` / `unmaximize` | 立即（这是离散事件） |
| 窗口关闭前 | 立即（`close` 事件里同步落盘） |

**最大化状态的坑**：最大化时 `getBounds()` 返回的是最大化后的尺寸，如果直接存下来，用户下次取消最大化就得到"最大化尺寸的普通窗口"。所以最大化时要单独存 `maximized: true`，并且**在最大化之前先记住 `getNormalBounds()`**（Electron 提供这个方法，专门给这个场景用）。

恢复逻辑：

```
if (maximized) → 先按 normalBounds 建窗口，再 win.maximize()
else           → 直接按保存的 bounds 建
```

### 5.4 与"关闭前 flush"的交互（步骤 03 的接口）

步骤 03 让主进程在 `close` 时先请渲染进程 flush。窗口状态的落盘也在 `close` 里，**顺序无所谓**（两者互不依赖），但都要在 `destroy()` 之前完成。合并写在一处，避免将来有人改了关闭流程漏掉其中一个。

## 6. 异常与边界

| 场景 | 处理 |
|---|---|
| `settings.json` 损坏 / 不是 JSON | 用默认值覆盖并写回，同时记一条 warning 日志。**不弹错误**：外观偏好不值得打断用户 |
| `schemaVersion` 不认识 | 同 sidecar 的策略（`03` 文档 §4.2）：报错并**保留原文件**（改名为 `settings.json.bak`），用默认值启动 |
| 保存的窗口尺寸小于 `minWidth/minHeight` | 建窗口时用 `Math.max(saved.width, minWidth)` 纠正 |
| 用户在设置里选了深色，但系统是浅色 | 显式 `data-theme='dark'` 优先，媒体查询不生效（§3.2 的 `:not()` 选择器保证） |
| 主题切换时渲染进程卡住 | CSS 变量是同步改的，无网络/无 IPC 依赖，不会卡 |
| 菜单里点"新建作品"但没有 sidecar | 渲染进程收到命令 → 走正常的失败路径（顶部状态条提示），菜单不需要感知 |
| `nativeTheme` 在系统主题变化时的通知 | 监听 `nativeTheme.on('updated')`，仅在 `mode === 'system'` 时同步 `data-theme` —— 让"跟随系统"实时生效，不用重启 |

## 8. 验收标准

| # | 项 | 判定 |
|---|---|---|
| 1 | 主题三态生效 | 选浅色 → 系统切深色，应用仍为浅色；选跟随系统 → 系统切深色，应用跟着变（**不用重启**） |
| 2 | 重启后保留 | 选深色 + 字号 18，退出重开 —— 仍是深色 + 18 |
| 3 | **深色下启动不闪白** | 在深色模式下反复重启 5 次，逐次观察：无白光 |
| 4 | 字号只影响编辑器 | 调到 22px，界面其他部分字号不变 |
| 5 | 菜单可用 | 逐个点一遍：新建作品、打开作品、关闭作品、退出、切换主题、放大/缩小/重置字号、打开日志目录 |
| 6 | **撤销（菜单路径）不坏文档** | §4.3 的用例：连打 10 段 → 菜单撤销 3 次 → 再打 → 保存 → 外部编辑器核对 md 结构正常 |
| 7 | 窗口位置尺寸恢复 | 拉到屏幕右下角、调整尺寸 → 退出重开 → 位置尺寸一致 |
| 8 | **拔显示器不丢窗口** | 在外接屏上放置窗口 → 退出 → 拔掉外接屏 → 重开：窗口出现在主屏可见处 |
| 9 | 最大化状态正确 | 最大化 → 退出 → 重开：是最大化；取消最大化后尺寸是最大化**之前**的 |
| 10 | 设置文件损坏可自愈 | 手动写坏 `settings.json` → 启动正常（用默认值），文件被重写为合法内容 |

第 3、8 两项是最容易被忽略、又最影响体感的两条。

## 9. 风险

| 风险 | 对策 |
|---|---|
| 菜单撤销与 ProseMirror 冲突，改坏文档 | §4.3 的两步策略 + 验收第 6 项强制实测。**这项必须在 M0 内实测，不能带着疑问进 M1** |
| 主题变量在两处重复，将来改一处忘另一处 | 两处相邻 + 互相注释指认；验收第 1 项会同时覆盖两条路径 |

## 11. 实现偏差与补充（v0.2）

设计文档与代码冲突时，**以本节为准**。

### 11.1 §6 最后一行那条 `nativeTheme.on('updated')` **不需要**，而且不该加

§6 建议"监听 `nativeTheme.on('updated')`，仅在 `mode === 'system'` 时同步 `data-theme`"。落地时发现这条通道是多余的：

`nativeTheme.themeSource` **本身就决定渲染进程里 `prefers-color-scheme` 的取值**。而"跟随系统"在渲染侧的表现恰好就是"**不写** `data-theme`、交给媒体查询"。于是：

| `mode` | `themeSource` | 渲染进程的 `prefers-color-scheme` | 结果 |
|---|---|---|---|
| `system` | `system` | 跟着操作系统实时变 | 媒体查询兜底块生效，**不用重启** |
| `light` | `light` | 恒为 light | 且 `data-theme='light'` 显式压住 |
| `dark` | `dark` | 恒为 dark | 且 `data-theme='dark'` 显式压住 |

好处是**只有一个真源**（`themeSource`）。真加了那条通道反而多出第二个真源 —— 而"设置里写着深色、界面却是浅色"这类不一致，正是本步骤开头要防的东西。

### 11.2 撤销/重做**直接走 §4.3 的第二步（保险方案）**，跳过第一步

§4.3 给的是"先按 `role` 实现再实测"的两步策略。这里直接走第二步，两个理由：

1. `role` 的语义**只能在真窗口里手工验**，而这条路径一旦错了代价是**文档损坏**（存盘存进去一堆乱结构）。用不着赌。
2. 更硬的一条：`role: 'undo'` **自带 `CmdOrCtrl+Z` accelerator**。一旦注册成菜单快捷键，键盘那条路会被菜单劫持（Electron 的 accelerator 先于页面 keydown）—— 于是**普通输入框**里按 Ctrl+Z（比如新建作品表单）会被转发给编辑器，输入框自己的撤销就没了。

所以菜单的「撤销/重做」是 `sendCommand('editor:undo' / 'editor:redo')` → `EditorHandle.undo()` → `editor.commands.undo()`，**且刻意不给快捷键**，键盘路径完整留给 ProseMirror 的 keymap（那条本来就是对的）。

### 11.3 `themeToDataTheme('system')` 返回 `null`（删属性），不是 `''`

§3.2 的示例代码是 `dataset.theme = mode === 'system' ? '' : mode`。`''` 写出来的是 `data-theme=""` —— **属性存在、值为空**，语义是"显式指定了一个空主题"。

危险的地方在于它**没有症状**：CSS 侧的 `:not([data-theme='light']):not([data-theme='dark'])` 对 `data-theme=""` 仍然匹配，一切照常工作，直到有人换一种选择器写法才炸出来。

已改成返回 `null`、调用点 `delete root.dataset.theme`，这条也写进了 `shared/settings.ts` 的注释和单测。

### 11.4 `editor.css` 的字号/行距初值对齐成 16px / 1.8

步骤 02 留的是 `15px / 1.9`，而 §3.3 定的是 `16px / 1.8`。已对齐 —— **不对齐会看到一次跳变**：样式表给的是"JS 还没跑起来时"的初值，渲染进程一挂载就用内联变量覆盖它，两个值不同就是一次肉眼可见的字号跳动。

### 11.5 `--editor-mask-bg` 从 `editor.css` 移到 `global.css`

它跟着 `--bg` 一起翻主题（半透明值没法用 `var(--bg)` 算出来）。留在 `editor.css` 就得在那里**再抄一份深色块**；移到 `global.css` 则是往已有的三个块各加一行。

选后者的另一个理由：留在 `editor.css` 会出现"两个文件都在 `:root` 上声明同一个变量"，谁赢取决于两个 CSS 文件的加载顺序 —— 那种胜负太脆。

### 11.6 「关闭作品」必须先 flush 再离开（一条 §5.4 没覆盖的丢字路径）

`work/leave` 会卸载 `WorkShell`，`useAutosave` 的清理函数随即 `dispose()` 掉实例 —— 防抖窗口里那批还没写盘的改动跟着实例一起消失。`07` §3 的时序只覆盖了"切章前 flush"，**没覆盖"离开作品"**。

处置：菜单的「关闭作品」与头部的「返回入口」都改走同一个 `closeWork`：

```
await autosave.flush()
├─ true  →（记下入口意图）→ dispatch work/leave
└─ false → 留在原地 + 通知条说明"还有未落盘的内容"，不离开
```

失败时**不离开**是关键：那时离开等于把用户的正文丢掉，而他看到的只是"界面回到了入口页"，没有任何线索。通知条与"切章被拦下"共用同一处（两者天然互斥）。

### 11.7 外观面板**常挂载**，关闭只是 `return null`

主题与字号是 `useAppearance` 的 effect 写到 `<html>` 上的。如果"关闭面板"表现为卸载组件，那么关掉面板就会把刚设好的主题一起撤掉 —— 属性还在，但不再有代码维护它，紧接着一次系统主题变化就再也不同步了。

所以面板由 `App.tsx` 常挂载，且**放在会话 Provider 之外**：主题是应用级外观，sidecar 挂了、停在入口页、看错误页，配色都必须是用户选的那个。

顺带一个层级决定：面板 `z-index: 90`，**低于**冲突对话框的 100。两者可能同时在场，而"你的稿子可能被覆盖"比"调字号"更该被看到。

### 11.8 字号/行距滑块每动一格就写一次盘

`updateTheme` 是"先改本地 CSS 变量、再 fire-and-forget 落盘"，所以拖一次滑块（14→22）会产生约 8 次原子写。M0 不加防抖：面板是模态的、拖动是有界动作，本机每次写是毫秒级；加防抖反而要处理"关面板时还有一次没落盘"。

### 11.9 `test/**` 读不了 `node:fs`（`tsconfig.web.json` 的 `types` 里没有 node）

`apps/desktop` 的测试全部归 `tsconfig.web.json`（`"types": ["vite/client"]`），`import fs from 'node:fs'` 直接 `TS2591`。

所以"`WINDOW_BG` 与 `global.css` 的 `--bg` 同值"这条断言改用 Vite 的 `?raw` 导入样式表原文。**但这还不够** —— Vitest 默认会把所有 CSS 请求的模块内容替换成 `''`（判定正则 `/\.(css|…)(?:$|\?)/` 连 `global.css?raw` 一起匹配），断言会拿到空串并永远失败，而失败信息是 `expected '' to contain …`，看着像路径写错了。处置是 `vitest.config.mts` 里的 `css: { include: [/global\.css/] }`，只放行这一个文件。

> 刻意不写 `css: true` 全量放行：实测那会让这个包的测试从 ~1.4s 涨到 ~7s（每个模块都要过 CSS 插件链）。只放行一个文件是 ~3s。

### 11.10 §4.2 的菜单结构里加了「外观设置…」

v0.1 的菜单结构只有"主题"的单选子菜单与字号三项。实际加了一项 **视图 → 外观设置…**（发 `settings:openPanel`）：档位只有单选和 ±，用户调不到"行距"。

> **2026-09-23 更新**：这一项已改名为 **视图 → 设置…**（命令通道不变，仍是 `settings:openPanel`）。
> 面板也从"只有外观"变成两个分区（外观 / AI 模型，见 `docs/11` P0），
> 相应地重命名：`AppearancePanel.tsx` → `SettingsPanel.tsx`、`use-appearance.ts` → `use-settings.ts`、
> `appearance.css` → `settings.css`（类名 `.appearance-*` → `.settings-*`）。
> 所以**下面 §12 的验收清单里凡是写「外观设置」的地方，都按「设置」找**，
> 面板里第一眼看到的是「外观」页签。
>
> **同日第二处微调**：「帮助 → 打开日志目录」原先 `shell.openPath(app.getPath('userData'))`
> —— 打开的是 **userData 本身**，与文案不符（`logs/` 只是它下面的一层）。改为打开 `<userData>/logs`
> 子目录，并在打开前 `mkdirSync`（尚未拉起过 sidecar 时该目录可能不存在，而 `openPath` 对不存在的
> 路径只返回一段错误字符串、界面毫无反应）。顺带把 `<userData>/logs` 的构造收敛到新增的

### 11.11 第一轮代码审查后的修复（M1–M3、L1–L2）

§12 落地之后做了一轮只诊断的代码审查，找出 5 个 medium、8 个 low。第一批修掉的是下面五项：

| # | 问题 | 处置 |
|---|---|---|
| M1 | `captureWindowState` 只在**最大化**时取 `getNormalBounds()`。最小化时 Windows 把窗口挪到屏幕外，`getBounds()` 给出 `-32000` 附近的坐标 —— 而最小化会触发 `resize`，500ms 后防抖的 `save()` 就把这对坐标写进了磁盘 | 判断改成 `isMaximized() \|\| isMinimized() ? getNormalBounds() : getBounds()`。**一处即覆盖两条写盘路径**（防抖 `save()` 与关窗 `destroyWindow()`） |
| M2 | `closeWork` 里 `await handle.flush()` 的 rejection 没人接（两个调用点都是 `void closeWork(...)`）→ 点「关闭作品」**毫无反应**，控制台一条 unhandled rejection | 按 `chapter-switch.ts` 的同款写法包 try/catch，失败收敛成 `setCloseBlocked` |
| M3 | `updateSettings`（IPC **写**路径）不校验 `mode`，而读路径有 `parseThemeMode` 兜着 | 把"合并 + 收敛"抽成 `settings-io.ts` 的 `mergeThemeSettings` / `coerceThemeMode`（纯逻辑），读路径与写路径共用同一份判断 |
| L1 | `APPEARANCE_RANGE` 是死导出（注释还写错了用途） | 删掉 |
| L2 | 冲突解决后 `closeBlocked` 残留，要用户手动点掉 | 冲突/保存错误解除时清掉 |

**M1 的严重度比初判轻**：`ensureOnScreen` 已经在建窗口前把越界坐标清掉，所以症状不是"窗口跑到屏幕外看不见"，而是**位置记忆丢失（下次启动回居中）**。真正的依据来自 Electron 文档：`getNormalBounds()` 在最大化、最小化、全屏下都返回"普通状态"的位置尺寸 —— 不必再猜 Windows 的行为。

**M2 的根因比"flush 会抛"更具体**：`Autosave` 把落盘错误都按错误码分类吞在 `attemptSave` 的 try 里，但**第一行 `this.opts.getMarkdown()` 在 try 之外** —— 编辑器序列化一旦抛（文档里进了 schema 应付不来的节点就会），异常一路穿过 `runLoop` → `pump()` → `flush()` → `closeWork`。同理 `onStateChange` / `onConflict` / `onError` 三个回调里的抛错也没人接。

**M3 的两个分支都要知道**：`nativeTheme.themeSource = '认不出的值'` 若**抛**，广播订阅会在那一行中断，`broadcastSettings` 与 `installAppMenu` 一起被跳过；若**不抛**（被静默忽略），`parsed.value` 里就留着坏值 —— 而 `loadSettings()` 走内存缓存、不回读文件，**要重启才自愈**，其间面板三个单选框全不选中，`themeToDataTheme('darkk')` 写出 `data-theme="darkk"` 只剩媒体查询兜底。修法对两个分支都成立。

### 11.12 补上 `will-navigate` 拦截

`setWindowOpenHandler` 只管 `window.open` / `target=_blank`，**管不到 `<a href>` 的普通跳转**。那种跳转会把应用窗口变成一个没有 preload 的外部页面 —— 没有地址栏、没有后退按钮，用户只能重启应用。

当前正文的 md 白名单还造不出链接，但编辑器早晚要渲染链接（批注定位、引用出处），所以现在补上：非 dev server 的导航一律 `preventDefault()`，http(s) 交给系统浏览器（与 `setWindowOpenHandler` 同一口径）。

**dev 必须放行 dev server**：它的全量刷新走 `location.reload()`，也算"页面发起的导航"，一律拦会把 HMR 弄坏 —— 而症状（改了代码页面不更新）很容易被误判成 Vite 的问题。因此 `devUrl` 的声明被提到了监听之前。另注 Electron 44 的回调签名是 `(details)` 而不是旧的 `(event, url)`。

### 11.13 `sandbox` 试开过，实测受阻后回退

从代码看它本可以开：preload 只用 `contextBridge` 与 `ipcRenderer`（这两个在沙箱 preload 里照样可用），其余 import 全是 `import type`、编译期就被擦除。

**但对照实验证明它会让窗口起不来**（2026-09-28，唯一变量就是这一行）：

| `sandbox` | 结果 |
|---|---|
| `true` | 主进程日志出现 `Render frame was disposed before WebFrameMain could be accessed`（触发点是 `broadcastStatus` 里第一次 `webContents.send`），窗口**始终不显示** —— `ready-to-show` 没触发，进程表里查不到「砚台」 |
| `false` | 窗口正常出现（`MainWindowHandle` 非 0，标题「砚台」） |

归因明确，**但不能直接外推**：实验是在一个受限执行环境里做的（Chromium 的渲染进程沙箱在 Windows 上要建受限令牌与 Job Object，套进已有的受限作业会失败）。普通终端里 `true` 可能是好的 —— 这需要一个"没有外层沙箱"的终端复跑一次才能定。

**取舍：未经验证的加固不如不加。** 出问题的症状是"窗口不出现"，而日志只有一句含义模糊的 frame dispose —— 与小方同学最反感的那类"看起来像别的问题"完全同型，排查成本远高于它挡掉的风险（渲染进程只加载自家页面，远程内容的口子已由 CSP 与 `will-navigate` 收掉）。

所以**保留 `sandbox: false`**，把结论与复验方式写进 `window.ts` 的注释，等步骤 07 在干净环境里复验。

### 11.14 第二轮代码审查后的窗口侧补强（`docs/13` 第 5 批的 M12/M13/M14）

三处都在 `window.ts`，都属"现在不可达、将来会可达"那一类 —— 由 §11.12 自己那句"编辑器早晚要渲染链接"引出的债务：

| 项 | 改动 | 为什么现在补 |
|---|---|---|
| M12 | `devUrl` 加 `app.isPackaged ? undefined : process.env['ELECTRON_RENDERER_URL']` | 打包产物里那个环境变量**依然读得到**。不设门禁时，"`ELECTRON_RENDERER_URL=https://evil.example` 再启动"就能让窗口带着 preload 去加载远程页，`contextIsolation` 护着的那套 API 等于交出去 |
| M13 | `will-navigate` 的内联体抽成 `guardNavigation`，与 `will-redirect` 共用 | 二者拦的不是同一类跳转：**服务端 302 与 `<meta http-equiv="refresh">` 走 `will-redirect`**。只挂 `will-navigate` 时，一个能控制响应头（或所在域 CDN 被接管）的页面就能把应用窗口带走。抽成具名函数而不是复制一段，是不给"只改一处"留机会 |
| M14 | `loadURL` / `loadFile` 各补 `.catch(reportLoadFailure)` | `void` 只让 lint 闭嘴、**并不接住它**；两者确实会 reject（dev server 没起来、`index.html` 缺失），漏掉就是一条 unhandledRejection + 一块白屏。现在至少以可读形式进日志 |

同批的 `index.ts` 进程级兜底（`uncaughtException` / `unhandledRejection`）与 IPC 入参校验见 `docs/10` §11.5 的第 5 批各行 —— 那两处不属于步骤 06 的范围，但都改在窗口关闭链路上（`app:flushResult` 载荷非法会让**窗口永远关不掉**），所以一起记在这里备查。

### 13.3 根因层面的问题：这道白屏在设计上不可诊断

与那个具体 bug 无关、但**任何一个渲染期异常都会退化成"无提示白屏"**的两个缺陷：

1. **主进程一条都不转发** —— `console-message` / `render-process-gone` / `unresponsive` /
   `did-fail-load` / `preload-error` 全都没接。渲染进程的报错只活在 DevTools 里，而 dev 态的
   DevTools 是 `openDevTools({ mode: 'detach' })` 开的**独立窗口**，很容易被主窗口挡住 ——
   现场就发生了"找不到 Console"。
2. **没有 ErrorBoundary** —— React 19 在无边界时会把**整棵根卸载**，这就是"连 header 都不剩"的机制。

### 13.4 落地内容（A + B）

**A. 可观测性** —— 新增 `src/main/renderer-diagnostics.ts`：

| 读数 | 含义 |
|---|---|
| `[hb] main alive`（5s 一次，仅 dev） | 主进程活着。**心跳停 = 主进程卡住**（菜单归主进程，所以"菜单也点不动"必然指向它） |
| `[renderer] warning / error …` | 渲染进程的 console，含 React 的未捕获异常栈 |
| `[renderer] unresponsive` / `responsive` | 渲染进程卡住 / 恢复 —— 把"卡住"与"抛异常"分开 |
| `[renderer] gone reason=… exitCode=…` | 渲染进程进程级消失 |
| `[renderer] preload-error …` | preload 挂了（症状是"界面正常但功能全失效"） |
| `[renderer] did-fail-load …` | 主框架压根没加载起来 |

只转发 `warning` / `error`：`info` / `debug` 里混着 Vite 与 React 的日常输出。
`menu.ts` 另加 `[menu] <路径>` 留痕（13 项自实现的 `click`），用来区分**点击没送进主进程**
与**送到了但看不出效果**（命令投给了一个已卸载的渲染进程）。
`renderer/src/main.tsx` 加全局 `error` / `unhandledrejection` 监听，把它们也送进同一条通道。

> `role` 那几项（剪切/复制/粘贴/全选/退出/全屏/重新加载/开发者工具）由 Electron 内部派发，
> **没有回调可挂** —— 它们有没有响应只能靠副作用判断。

**B. 兜底界面** —— 新增 `src/renderer/src/components/ErrorBoundary.tsx`，在 `App.tsx` 里包住整棵界面：
崩溃时渲染一张卡片（`名称: 消息` + JS 栈 + 组件栈 + 「重新加载界面」），不再是一片白。
`componentDidCatch` 走 `console.error` 而不是自己写文件 —— 复用 A 的统一通道。

配套改动：`window.ts` 的 `will-navigate` 增加"**URL 与当前完全相同**即放行"。
不加的话兜底页的「重新加载界面」在生产态会被这条监听自己拦掉（那时 URL 是 `file://`，

### 13.7 根因：编辑器句柄抱住了一个已销毁的实例

B 上线后用户再复现，卡片给出的栈是：

```
TypeError: Cannot read properties of null (reading 'commands')
The above error occurred in the <EditorPane> component.
  get commands (…/deps/dist-C2tklgZr.js:14282:30)
  Object.setMarkdown (…/features/editor/TipTapEditor.tsx:86:12)
```

即 `handle.setMarkdown()` → `editor.commands.setContent(...)` → 在 `get commands()` 里炸。

**先否掉一个我当时很确信的假设。** 起初的判断是"`create` 是在 `setTimeout(…, 0)` 里发的，
到它触发时实例已经被换掉了，所以 `onCreate` 的**载荷**是死实例"。读源码后**这个假设不成立**：

```js
// @tiptap/core 6234–6238
mount(el) {
  …
  window.setTimeout(() => {
    if (this.isDestroyed) return;      // ← 载荷一定有这道闸，不可能是死实例
    …
    this.emit("create", { editor: this });
  }, 0);
}
```

**真实机制是"句柄的寿命比实例长"。** 两条都实测确认过的事实：

1. `get commands()` 就是 `return this.commandManager.commands`（core 6271–6272），
   而 `commandManager` **只在 `destroy()` 里被置成 `null`**（core 6624，构造函数在 6424 建立它）
   —— 所以"读 `commands` 抛 null"⟺ **这个 Editor 已经销毁**。
2. `@tiptap/react` 里销毁 Editor 的地方只有两处：`refreshEditorInstance`（react:423）
   与 `scheduleDestroy` 的 1ms 定时器（react:441）。后者在 `isComponentMounted` 为假时开火
   —— 也就是**组件卸载时**。

而旧代码里**句柄只在 `onCreate` 里造一次**，`create` 之后没有任何时机重建它。
于是只要实例在句柄还活着的时候被销毁，句柄就永远指着一具尸体。本应用里这条**可达**：

| 卸载点 | 位置 | 触发条件 |
|---|---|---|
| `WorkShell` 整树返回 `null` | `WorkShell.tsx:259` | `state.kind !== 'ready'` |
| `EditorPane` 只渲染占位 | `EditorPane.tsx:114` | `chapter === null` |

（先把"实例被销毁"与"实例被丢弃"分开记：`scheduleDestroy` 在 `isComponentMounted` 为假时
还会 `setEditor(null)`，那时 `useEditor` 返回 `null`，是另一种形状。）

**为什么一次本来可恢复的失败会升级成整树卸载。** 旧 `setMarkdown` 的 `catch` 里做兜底时
**又去调了同一个死实例的 `commands`** → 二次抛出 → 逃出 `EditorPane` 的 effect →
React 19 在没有错误边界时卸载整棵根 → **连 header 都不剩**。所以第 8 节修的不是"崩溃"，
是"崩溃被放大成全白"。

**修法（`TipTapEditor.tsx`）**：句柄改成**一组"把命令交给当前编辑器"的函数**，不持有实例 ——
`makeHandle(() => editorRef.current, markdownCache)`，`onCreate` 刻意忽略事件载荷；
每个动词先过 `usable()`（`editor.isDestroyed` 是 TipTap 官方判据），不可用就安全退化。
`describeUnusable()` 会把两种失效分开写进日志（"实例不存在" / "实例已销毁"）——
下次再出问题，这一行直接给出答案。

**"读正文"是唯一不能退化成空动作的动词**，因为它的返回值会被直接写盘：

- 返回 `''` → `Autosave` 把空文件写盘，直接覆盖用户手稿；
- 抛异常 → `Autosave.attemptSave()` 是在 `try` **之外**调它的（`autosave.ts:301`），
  而 `runLoop` 在调用**之前**已经把 `mustSave` 清成了 `false`（`autosave.ts:289`）。
  异常只会变成一个无人接收的 rejection —— **改动既没落盘、也不会进重试、界面上还什么都不说**。
  （`EditorPane.handleChange` 那条路更糟：它同步跑在 TipTap 的 `onUpdate` 里，
  即 ProseMirror 的事务派发中，异常会直接打断编辑。）
- 所以它退化成"返回最近一次已知正文"（`markdownCache`，在 `getMarkdown` / `setMarkdown`
  成功时刷新；`setMarkdown` 存的是 `toMd(doc).markdown`，保证与真实读取口径一致）。

> ⚠️ **`markdownCache` 跨章存活。** 切章时 `content` 只换值、组件不重挂
> （`EditorPane` 与 `TipTapEditor` 都没有 `key`，而且 `use-chapter-switch.ts:154` 的
> `setContent` 从不传 `null`）—— 所以 `setMarkdown` 成功时必须顺手刷新缓存，
> 否则里面留的是**上一章的正文**，一旦命中安全网就会把上一章写进这一章。
